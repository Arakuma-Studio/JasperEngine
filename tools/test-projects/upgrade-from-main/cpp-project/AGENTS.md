# JasperEngine Project Context

This project was generated by JasperEngine Editor version `d61bed5a5-dirty`.

## Working with the editor (MCP)

JasperEngine Editor embeds an MCP server: build scenes, prefabs, UI and project settings, and playtest, through its tools instead of editing `*.scene`/`*.prefab`/`project.yaml` by hand (the open editor would overwrite such edits). Start it with `jasperengine-editor mcp --project <this directory>` as a stdio MCP server, or attach to an editor that is already open over HTTP (Window > MCP: `http://127.0.0.1:47615/mcp` by default, with the bearer token that window copies). The server's instructions and the `jasper://guide` / `jasper://docs/...` resources explain the tools.

- Scripts, shaders and other text files: edit them on disk with your own tools. The editor picks the changes up automatically before every MCP tool call (the call's result lists them under `external_changes`, with problems such as Lua syntax errors); no sync step is needed.
- Lua API: one stub file per engine class in `.jasperengine/engine-api/lua/`, and the class of each project script (its properties as fields) in `.jasperengine/engine-api/lua/scripts/`, for lua-language-server (`.luarc.json` at the project root points at them). Start a script module with `---@class <FileName> : ScriptInstance` (the templates do) so `self` is typed.
- C++ API: the headers in `.jasperengine/engine-api/`; `.clangd` (with `.jasperengine/clangd/compile_commands.json`) lets clangd resolve them, e.g. `clangd --check=scripts/Player.cpp`. C++ scripts build when a scene plays, or with the `compile_scripts` tool.
- Features with their own reference (`jasper://docs` lists them all), e.g. the GPU fluid simulation (Fluid Simulation component: `create_entity` type `fluid_simulation`, presets, seeded deterministic runs, Lua `FluidSimulation`; `jasper://docs/fluid`) and post-processing (`jasper://docs/post-processing`).
- Keyframe animation: Animation Clips are shared `.anim` JSON assets whose tracks bind by path below the GameObject that plays them, played by an Animation Player component (Unity's legacy Animation; Lua `getAnimationPlayer()`, `play`, `crossFade`, `queue`, clip events into script methods). Edit them with `edit_animation {clip, ...}` (one project undo step) or by hand (auto-sync reloads them and reports problems); a model's animations are read-only clips `assets/models/hero.gltf#Walk`. Guide: `jasper://docs/animation`.
- Checks without the editor: `jasperengine-editor check --project . [--files <paths...>] [--cpp]` (Lua syntax and load, shaders, animation clips, vertex animations, HTML/CSS UI, C++ build; exit code 1 on errors). As an agent hook after every edit, shell commands included: `jasperengine-editor check --project <this directory> --hook` (PostToolUse; it checks what changed since its last run and logs to `.jasperengine/check-hook.log`).

## HTML/CSS UI

Game UI (menus, HUDs, dialogs) is written in standard HTML and CSS with Lua logic, one document per GameObject (UI Document component; MCP: `create_ui_document`). Put documents under `assets/ui/`. There is no JavaScript: a `<script>` or `onclick` is reported; use the Lua element API (`UIDocument(self.scene, self.entity):querySelector(...)`, `addEventListener`, `classList`, data models, `anime.animate`). `jasperengine-editor check --ui` (also in the default check and the hook) reports every construct the engine drops or rewrites, with file:line:col and a fix. A page without a background lets the pointer through to the documents below and the game unless it listens for the pointer. GPU effects go in CSS as `effect(<name>, <param> <value>, ...)` in `background-image`, `mask-image`, `filter` and `backdrop-filter` (catalogue: `jasper://docs/html-ui-effects`, stateful simulations such as `fog` and `ink-flow` included; a project's own effect is a `.frag` declared with `@effect`). `<video>` plays AV1 + Opus WebM (`import_files` converts other formats with a user-installed FFmpeg). Supported CSS: the `jasper://docs/html-ui-support` resource; guide: `jasper://docs/html-ui`; complete examples to copy: `.jasperengine/engine-api/html-ui-examples/`.

## Generated files

These files are produced by the editor when a scene is played/run and are intended for **local development and testing**. Project export/distribution uses a separate pipeline and does not reuse these files. Do not edit them manually — they will be overwritten on the next generation:

- `CMakeLists.txt` (project root)
- `.jasperengine/LocalPaths.cmake` (paths belonging to this machine, included by `CMakeLists.txt`)
- `.jasperengine/scene_scripts.cpp`
- `.jasperengine/generated/` (scene factories, prefab factories, `main.cpp`)
- `.jasperengine/engine-api/` (engine API snapshot copied from the editor)

## Version control

`project.yaml`, `*.scene`, `*.prefab`, `ProjectBuild.cmake`, `AGENTS.md` and the assets describe the game and are meant to be committed. Everything under `.jasperengine/` is not: it holds the engine API snapshot and generated C++, the build settings for this machine (`user/build.yaml`), this developer's editor layout and viewport cameras (`user/workspace.yaml`), and whatever the game writes through `data://` during Play (`user/rundata/`). The editor regenerates all of it when the project is opened or built.

`CMakeLists.txt` is regenerated too and is ignored for the same reason. It contains no machine-specific path: asset and Lua roots resolve from `${PROJECT_ROOT}`, and the shader cache comes from `LocalPaths.cmake`.

Do not move per-user or per-machine values into `project.yaml`; a value that differs between two developers working on the same project belongs in `.jasperengine/user/`.

## Custom build settings

`CMakeLists.txt` is regenerated on every build, so edits to it are lost. Put your own build settings in `ProjectBuild.cmake` at the project root instead: the editor never writes that file, and both the editor and exported builds include it when it exists.

Use `${JASPERENGINE_TARGET}` instead of the literal target name, which differs between the two builds. `${JASPERENGINE_SCRIPTS_DIR}` is the root your `.h`/`.cpp` paths are relative to.

```cmake
target_include_directories(${JASPERENGINE_TARGET} PRIVATE ${JASPERENGINE_SCRIPTS_DIR}/Source/Game/Public)
target_link_libraries(${JASPERENGINE_TARGET} PRIVATE mylib)
```

## Regenerating C++ code

The generated C++ sources (scene factories, script bindings) are derived from `*.scene`, `*.prefab`, and `project.yaml` files.
After changing any `*.scene`, `*.prefab`, or `project.yaml` file, regenerate through JasperEngine Editor by playing/running the scene before validating the resulting build. This refreshes the generated sources, including `.jasperengine/generated/` and script bindings. If editor access is unavailable, report that regeneration and runtime validation remain pending.

## C++ Scripts

User C++ script files (`.h`/`.cpp`) can be placed anywhere in the project outside of `.jasperengine/`.
A script class attached to a GameObject's Script component either inherits `jasperengine::ScriptBase` (`#include "ScriptBase.h"`, general logic) or the GameObject's own class (`jasperengine::Mesh`, `jasperengine::Sprite`, ... to call its methods on `this`), and declares a `(jasperengine::Scene* scene, jasperengine::Entity entity)` constructor; fields marked `DPROPERTY("Name")` show in the Inspector. A `ScriptBase` script overrides the lifecycle it needs, as Lua scripts: `init()` (first activation, after its properties are bound), `onEnable()`, `start()`, `onDisable()`, `onDestroy()`. Ordinary helper classes and source files need neither. The editor discovers and registers scripts automatically; they are added to `SCRIPT_SOURCES` in the generated `CMakeLists.txt` and compiled into the project.
A directory listed as a script root (JasperEngine Editor: Project Settings > Directories) is compiled whole: source files are built even when no component references them. Discovery skips hidden directories and directories named `build`. The root is an include directory, so a header at `<root>/PLAYER/Thing.h` is included as `PLAYER/Thing.h`.
The C++ language standard is Project Settings > Build > C++ Standard (`cxxStandard` in `project.yaml`): 17, 20, or 23. Play and export both build with it; do not edit `CMAKE_CXX_STANDARD` in the generated CMakeLists.txt.
Lua scripts (`.lua`) are separate — they are loaded at runtime and are not compiled into the binary.

## Instantiate and Destroy (prefabs at runtime)

Unity's Object.Instantiate / Destroy are `GameObject::instantiate`, `GameObject::destroy(object, delay)` and `GameObject::destroyImmediate` (Lua: `GameObject.instantiate`, `GameObject.destroy`, `GameObject.destroyImmediate`). `instantiate` takes a `PrefabAsset` (a script property of type Prefab, or `PrefabAsset::load("enemies/EnemyShip")`) or any GameObject to copy, then optionally a parent (+ `instantiateInWorldSpace`) or a world position and rotation (+ parent). It returns the new root, named `<name>(Clone)`, with the scripts of every new GameObject already started (Lua `init`, C++ constructors). A copy keeps the components and script property values; references among the copied GameObjects point to the copies. `destroy` removes the GameObject and its children after the frame's update (or `delay` seconds later), calling Lua `onDestroy` and C++ destructors first.
`PrefabManager` is the registry behind it: `registerPrefab(id, name, guid, factory)` is called by the generated `main.cpp` for every prefab of the build, ids in path order (the same ids the editor's Play uses). A factory builds the prefab on the bare root it is given and returns `bool`. Each prefab header also declares `build_prefab_<name>(scene, root, members)`, the same factory appending the entities it creates to `members` in a fixed order; generated scene sources address instance entities through it, since their ids only exist at runtime.
The build holds the prefabs scenes instantiate, the ones script properties of type Prefab reference, the ones listed under `standalonePrefabs` in `project.yaml` (JasperEngine Editor: Assets > Prefabs), and the prefabs those nest or reference. `PrefabAsset::load` finds a prefab of the build by path, name or GUID, and reports any other as not found.

## Build modes

- **Editor mode** (`JASPERENGINE_EDITOR_PLUGIN=ON`): builds as a shared library; `main.cpp` and Factory-generated scene sources are excluded. Used by the editor to hot-reload the project.
- **Standalone mode** (`JASPERENGINE_EDITOR_PLUGIN=OFF`, default): builds as an executable; includes `main.cpp` and all Factory sources. This standalone build is for local testing only — production distribution uses the editor's separate export pipeline.

Both modes link the editor's engine library, which always has Box2D and Jolt. Project Settings > Build > 2D/3D Physics (`physics2D`/`physics3D` in `project.yaml`) only affects the export, which rebuilds the engine without a disabled backend; code that must build either way guards on `JASPERENGINE_PHYSICS_2D`/`JASPERENGINE_PHYSICS_3D`. `RayFilter::BOUNDS` ray casts against mesh bounds and needs neither.
