# Code tools and language servers (Lua and C++)

Every JasperEngine project carries the engine API on disk, so a coding agent (Claude Code,
Codex) or an editor works on scripts with its own tools: grep, file reads, and the
lua-language-server and clangd language servers. Nothing here needs the MCP server.

The editor writes these files when it opens a project and again on every build (Play,
`compile_scripts`), so they always match the engine of the editor that last opened it:

| File | What it is |
|---|---|
| `.jasperengine/engine-api/lua/*.lua` | Lua API stubs (LuaLS / EmmyLua annotations) generated from the engine's Lua bindings: one file per class (`Vector3.lua`, `Sprite.lua`, `Engine.lua`...) and per enum (`CameraType.lua`), plus `Globals.lua` (`RegisterEngineEvent`, `RegisterEvent`, `NULL_ENTITY`, the Engine event names) and `Script.lua` (the script module contract: `ScriptInstance`, `properties` entries). |
| `.luarc.json` | lua-language-server settings: `runtime.version` (the engine's Lua, 5.4) and `workspace.library` pointing at the stubs. An existing file is merged into: only a missing library entry or Lua version is added, other keys are kept. |
| `.jasperengine/engine-api/` | C++ engine API headers (the snapshot C++ scripts compile against). |
| `.jasperengine/clangd/compile_commands.json` | Compile commands of every C++ source of the project: the C++ standard from Project Settings, the definitions and include directories of the plugin build. Absolute paths, rewritten on open and build (a moved project is fixed the next time the editor opens it). `engine_api.cpp` next to it includes the whole engine API so clangd indexes it. |
| `.clangd` | Points clangd at that compile database. The editor only rewrites a `.clangd` whose first line is its `# Generated by JasperEngine Editor.` marker: delete that line to keep your own edits. |

`.jasperengine/` is ignored by version control (the editor's `.gitignore`); `.luarc.json` and
`.clangd` hold only project-relative paths and may be committed. None of these files is
exported with the game.

## Reading the API

The stubs are plain Lua files meant to be read and grepped:

```sh
grep -n "function Sprite:" .jasperengine/engine-api/lua/Sprite.lua    # methods (colon call)
grep -n "^---@field" .jasperengine/engine-api/lua/Engine.lua          # properties, static ones marked (static)
grep -rn "setColor" .jasperengine/engine-api/lua/                     # who has it
```

- `---@class Sprite : Mesh`: methods and properties are inherited, read the base class too.
- `---@overload fun(scene: Scene, entity: integer): Sprite` on a class is a constructor:
  `Sprite(self.scene, self.entity)`.
- `function Vector3:length()` is called with a colon (`v:length()`); `function Input.isKeyPressed(key)`
  is static, called with a dot.
- Field notes: `(read-only)` cannot be assigned, `(copy)` returns a copy (assign a new value
  to change it: `obj.position = Vector3(...)`, not `obj.position.x = 1`), `(event)` is an event
  object (subscribe with `RegisterEvent`).
- A name that is not in the stubs is not bound to Lua: do not guess C++ names.
- Lines starting with `---` above a declaration are its documentation (from the engine headers).

## Lua: lua-language-server

Install it from https://github.com/LuaLS/lua-language-server/releases (it is not an engine
dependency). Check the whole project from its root:

```sh
lua-language-server --check=. --checklevel=Warning --check_format=json --check_out_path=/tmp/luals.json
```

It reports unknown globals, unknown methods and fields of engine classes, wrong argument
types and counts, and unknown Engine event names in `RegisterEngineEvent`. An editor with the
Lua extension (VS Code: sumneko.lua) or an agent with a Lua LSP picks `.luarc.json` up by itself.

Annotate a script module as a `ScriptInstance` subclass to get checks on `self` (`self.scene`,
`self.entity` and the properties):

```lua
---@class Player : ScriptInstance
---@field speed number
---@field target Sprite
local Player = {
    properties = {
        { name = "speed", displayName = "Speed", type = "float", default = 5.0 },
        { name = "target", displayName = "Target", type = "Sprite" },
    }
}

function Player:init()
    RegisterEngineEvent(self, "onUpdate")
end

function Player:onUpdate()
    self.target.position = self.target.position + Vector3(self.speed * Engine.deltatime, 0, 0)
end

return Player
```

Without the annotation the script still checks, but fields of `self` are untyped.

## C++: clangd

Install clangd (e.g. `apt install clangd`, Xcode's, or LLVM's release; not an engine
dependency). It finds `.clangd` and the compile database by itself; no build is needed first.
Check one file:

```sh
clangd --check=scripts/Player.cpp
```

Headers and C++ files created after the editor last wrote the compile database get the flags
of the closest listed source, so a new script checks right away; the editor lists it on its
next open or build. The C++ standard is Project Settings > Build > C++ Standard
(`set_project_settings` `scripting.cxx_standard`).

The CMake build of the scripts (Play, `compile_scripts`) also exports its own
`compile_commands.json` in `.jasperengine/build`, for IDEs that read that one.
