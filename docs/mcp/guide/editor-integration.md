# Code tools and language servers (Lua and C++)

Every JasperEngine project carries the engine API on disk, so a coding agent (Claude Code,
Codex) or an editor works on scripts with its own tools: grep, file reads, and the
lua-language-server and clangd language servers. Nothing here needs the MCP server.

The editor writes these files when it creates or opens a project and again on every build
(Play, `compile_scripts`), so they always match the engine of the editor that last opened it:

| File | What it is |
|---|---|
| `.jasperengine/engine-api/lua/*.lua` | Lua API stubs (LuaLS / EmmyLua annotations) generated from the engine's Lua bindings: one file per class (`Vector3.lua`, `Sprite.lua`, `Engine.lua`...) and per enum (`CameraType.lua`), plus `Globals.lua` (`RegisterEngineEvent`, `RegisterEvent`, `NULL_ENTITY`, the Engine event names) and `Script.lua` (the script module contract: `ScriptInstance`, `properties` entries). |
| `.jasperengine/engine-api/lua/scripts/<Name>.lua` | The class of each Lua script of the project (`<Name>` = its file name): `---@class <Name> : ScriptInstance` with a `---@field` per entry of its `properties` table, typed as the engine sets it on `self` (`float` -> `number`, `Sprite` -> `Sprite`, `Prefab` -> `PrefabAsset`, `entity` -> `ScriptInstance\|EntityHandle`, another script's name -> that script's class). Read by running the script's top level in an isolated Lua state, as `jasperengine-editor check` does. Rewritten on open, when a script is saved in the code editor or created / renamed in the Project window, and when the editor picks up a changed script (before every MCP tool call, `sync_files`). Fields the script declares itself (`---@field`) are left out; a script that does not load keeps its last class; a script named like an engine class (`Camera.lua`) gets none. |
| `.jasperengine/engine-api/luals-plugin.lua.txt` | lua-language-server plugin generated with the stubs: it has assignments to the engine classes' static fields through the global table (`Engine.timeScale = "fast"`) checked against their types (see [below](#assigning-through-a-global-class-table)). Not a `.lua` file, so the server does not take it for a script of the project. |
| `.luarc.json` | lua-language-server settings: `runtime.version` (the engine's Lua, 5.4), `workspace.library` pointing at the stubs and `runtime.plugin` pointing at the plugin. An existing file is merged into: only a missing library entry, Lua version or plugin is added, other keys are kept; a file that lists plugins of its own gets the engine's first in the list (the server runs them in order and keeps the last one's result; the engine's passes the events it does not use on). |
| `.jasperengine/engine-api/` | C++ engine API headers (the snapshot C++ scripts compile against). |
| `.jasperengine/clangd/compile_commands.json` | Compile commands of every C++ source of the project: the C++ standard from Project Settings, the definitions and include directories of the plugin build. Absolute paths, rewritten on open and build (a moved project is fixed the next time the editor opens it). `engine_api.cpp` next to it includes the whole engine API so clangd indexes it. |
| `.clangd` | Points clangd at that compile database. The editor only rewrites a `.clangd` whose first line is its `# Generated by JasperEngine Editor.` marker: delete that line to keep your own edits. |

`.jasperengine/` is ignored by version control (the editor's `.gitignore`); `.luarc.json` and
`.clangd` hold only project-relative paths and may be committed. None of these files is
exported with the game.

## Paths and symbolic links

Tools take project-relative paths. Reads follow symbolic links (and Windows junctions) wherever
they lead, so an assets folder linked in from a shared library reads, lists and previews like any
other. The project folder and its configured assets and Lua scripts folders are trusted even when
they are links themselves (an assets folder on a shared drive): writes go there. A tool that writes, creates,
deletes, moves or renames a file refuses a path that a link BELOW those folders leads out of them
(an asset root can't be set to a folder outside the project either) (isError: the path, where the link leads, and the fix:
use a path that is not behind a link to elsewhere, or replace the link with a real folder). Links
that point inside the project work, and so does a project opened through a link. Deleting or
moving a link moves the link itself, never what it points at. A folder that becomes a link to
elsewhere after a write was made blocks its undo (`undo` fails with the file and "remove the link,
then undo again"; the history keeps its place).

## Reading the API

The stubs are plain Lua files meant to be read and grepped:

```sh
grep -n "function Sprite:" .jasperengine/engine-api/lua/Sprite.lua    # methods (colon call)
grep -n "^---@field" .jasperengine/engine-api/lua/Engine.lua          # properties, static ones marked (static)
grep -rn "setColor" .jasperengine/engine-api/lua/                     # who has it
```

- `---@class Sprite : Mesh`: methods and properties are inherited, read the base class too.
- `---@overload fun(scene: Scene, entity: integer): Sprite` on a class is a constructor:
  `Sprite(self.scene, self.entity)`.
- `function Vector3:length()` is called with a colon (`v:length()`); `function Input.isKeyPressed(key)`
  is static, called with a dot.
- Field notes: `(read-only)` cannot be assigned, `(copy)` returns a copy (assign a new value
  to change it: `obj.position = Vector3(...)`, not `obj.position.x = 1`), `(event)` is an event
  object (subscribe with `RegisterEvent`).
- A name that is not in the stubs is not bound to Lua: do not guess C++ names.
- Lines starting with `---` above a declaration are its documentation (from the engine headers).

## Lua: lua-language-server

Install it from https://github.com/LuaLS/lua-language-server/releases (it is not an engine
dependency). Check the whole project from its root:

```sh
lua-language-server --check=. --checklevel=Warning --check_format=json --check_out_path=/tmp/luals.json
```

It reports unknown globals, unknown methods and fields of engine classes, wrong argument
types and counts, and unknown Engine event names in `RegisterEngineEvent`. An editor with the
Lua extension (VS Code: sumneko.lua) or an agent with a Lua LSP picks `.luarc.json` up by itself.

Declare a script module as its `ScriptInstance` subclass to get checks on `self` (`self.scene`,
`self.entity` and the properties). The class name is the file name; the editor's templates
(`create_script`, the Add Script dialog, the Project window's Create > Lua Script) write the
line. The properties' fields come from the generated `scripts/<Name>.lua` class, so they need
no annotation of their own (a `---@field` you write wins over the generated one):

```lua
---@class Player : ScriptInstance
local Player = {
    properties = {
        { name = "speed", displayName = "Speed", type = "float", default = 5.0 },
        { name = "target", displayName = "Target", type = "Sprite" },
    }
}

function Player:init()
    RegisterEngineEvent(self, "onUpdate")
end

function Player:onUpdate()
    self.target.position = self.target.position + Vector3(self.speed * Engine.deltatime, 0, 0)
end

return Player
```

Without the annotation the script still checks, but fields of `self` are untyped and a typo
or a wrong method on a property (`self.target:notAMethod()`) goes unnoticed.

### Assigning through a global class table

A wrong type assigned to an engine property is reported on an object (`sprite.width = "x"`,
`go.position = 5`), through a local (`local engine = Engine; engine.timeScale = "fast"`) and
through the global class table itself: `Engine.timeScale = "fast"`, `Input.KEY_SPACE = {}`,
`Engine.scene = "main"` are `assign-type-mismatch`, for every static field of the stubs
(`(static)` in the field's note).

The last one needs the plugin. lua-language-server (3.x) reads an assignment to a field of a
global name as the definition of a global variable typed by the assigned value
(`vm/global.lua`: the set becomes the global `Engine.timeScale`, and `vm.compileByGlobal`
types it by its value), so the class's `---@field timeScale number` is never compared with it;
no form of the stubs changes that. The plugin (`runtime.plugin`) makes the server read such an
assignment as `(Engine).timeScale = ...` before it checks the file: only the syntax tree
changes, not the text, so positions and messages are the server's own; hover shows the field's
type and go to definition lands in the stubs. It is checked exactly as `obj.timeScale = ...`
would be, so `Engine.timeScale = tonumber(s)` is reported too (`number?`: `tonumber` may
return nil), as on an object. Only the static fields the stubs declare are concerned: a game's
own field on an engine table (`Engine.myFlag = true`) and the game's own globals
(`GameState = {}`, `GameState.level = 2`) are left as they were. Not covered: deeper chains
(`Engine.viewRect.x = ...`), `_G.Engine.timeScale = ...` and `rawset`.

Where the plugin runs:

- `lua-language-server --check`: always (the command-line check trusts the workspace's
  plugins).
- VS Code with the Lua extension (sumneko.lua): loaded without a question (the extension tells
  the server its client is trusted, `trustByClient`).
- Other editors (Neovim, Zed, Helix...): the server asks whether to trust the plugin at
  `.jasperengine/engine-api/luals-plugin.lua.txt` ("Trust and load this plugin"); once trusted,
  the path is remembered (the `trusted` file of the server's log directory), a refusal is asked
  again on the next start. Without trusting it, or in a client that cannot show the question,
  the plugin stays off: assignments through the global table are then unchecked, everything
  else works as before.

To silence one line, use `---@diagnostic disable-next-line: assign-type-mismatch`. The editor
adds the plugin back to `.luarc.json` whenever it opens the project, as it does the library.

## C++: clangd

Install clangd (e.g. `apt install clangd`, Xcode's, or LLVM's release; not an engine
dependency). It finds `.clangd` and the compile database by itself; no build is needed first.
Check one file:

```sh
clangd --check=scripts/Player.cpp
```

It prints the file's diagnostics as `E[...] [code] Line N: message` lines and ends with
`All checks completed, N errors`. (`--check-locations=false` skips the per-token feature checks;
with clangd 18 it printed the same diagnostics and count, so it is not needed for errors.)

Headers and C++ files created after the editor last wrote the compile database get the flags
of the closest listed source, so a new script checks right away; the editor lists it on its
next open or build. The C++ standard is Project Settings > Build > C++ Standard
(`set_project_settings` `scripting.cxx_standard`).

The CMake build of the scripts (Play, `compile_scripts`) also exports its own
`compile_commands.json` in `.jasperengine/build`, for IDEs that read that one.
