## 1. Intent

The repository is public now, so standard GitHub-hosted runners are free and have no minute cap. Work reaches
`main` through pull requests. The repository moved to the owner's organization (`Arakuma-Studio/JasperEngine`) so
it can use a merge queue.

What hurts most when it reaches `main` is **the engine not building, or games not building**. That covers every
platform. Tests matter, but second. Today nothing checks a push except what an agent ran by hand, and before
pushing, `AGENTS.md` asks for a local full suite that takes hours (the MCP suite alone took 5.2 h at `-j 2`,
`docs/testing.md:1177`).

This design gives:

- **A PR check.** Every PR gets a verdict within 1–2 hours: one required check, `Check`, and one sticky PR
  comment saying exactly what failed, with the command that reproduces it.
- **A full gate before landing.** The merge queue runs the full required set on the exact tree that will
  become `main`, so `main` stays green by construction.
- **A nightly.** The slow lanes run every night and the results land in one issue.
- **Published downloads.** Nightly and stable releases of the editor and every player runtime, unsigned.
- **An agent workflow built on it.** `CI owns the full suite` replaces the hand-run local full suite, so
  development gets faster, not only safer.

## 2. Goals

1. **G1 — nothing that fails to build reaches `main`.** The editor, the engine and a real game must build on
   every platform before landing:
   - Linux, Windows (MSVC), macOS and iOS (Xcode).
   - Web (Emscripten) and Android (Gradle).
2. **G2 — games build end to end.** A committed fixture project, and a project made from each template, is
   exported and launched by both methods: prebuilt player plus cooked assets, and Compile. This runs on Linux.
   The Compile build alone also runs with MSVC on Windows and with Clang on macOS.
3. **G3 — the right tests on every PR.**
   - On a PR: the unit, HTML UI and MCP tests that `tools/check-changed` selects for the diff.
   - In the merge queue: all of them, MCP sharded across runners.
4. **G4 — fast verdicts.**
   - PR, warm cache: p50 ≤ 60 min, p95 ≤ 120 min from push to `Check`.
   - Merge-queue group: ≤ 120 min.
   - These are targets to measure in rollout (§15), not promises.
5. **G5 — a failure explains itself.**
   - One comment per PR, updated by each run. It lists every failed job, the failing build lines, test names
     and assertions, the exact local repro command and links to the evidence.
   - The same text goes to the run's job summary.
   - A machine-readable JSON copy goes into an artifact for agents.
6. **G6 — downloads.**
   - Nightly prereleases are published only when `main` moved.
   - Stable releases are cut from a version and rebuild the commit of the latest nightly.
   - Each release carries the editor for Windows, Linux and macOS, every player runtime, and `SHA256SUMS`.
     Everything is unsigned. A release is a draft until every asset is attached.
7. **G7 — one way to reproduce a failure.**
   - Every CI step is a one-line call to a script in the repository that runs the same way on a developer's
     machine.
   - Linux, Web and Android lanes use `tools/build.sh` in the same Docker images.
   - Windows and Apple lanes use new `tools/ci/*.sh` scripts. No logic lives only in YAML.
8. **G8 — agents develop faster.**
   - `AGENTS.md` moves the full suite to CI and adds a PR workflow: open, watch `Check`, read the report,
     fix, push.
   - It adds a "hit every surface" report to the PR body, and test-economy rules.
   - A PR template and `CONTRIBUTING.md` land too.

## 3. Non-goals

- **Code signing and notarization.** The owner decided to ship unsigned (§12.5). No signing hooks or unused
  secrets get added.
- **CI for game projects.** The owner decided a game's CI is the game author's business. The editor writes no
  workflow into projects.
- **GPU runners, larger runners or self-hosted runners.** The first two are billed even on public repos. A
  self-hosted runner on a public repo runs any PR author's code.
- **A second change detector in JavaScript or YAML.** CI reuses `tools/check-changed` (§6).
- **PR hygiene bots from t3code:** vouching, open-PR limits, size labels, stale sweeps and test-delta comments.
  They solve heavy outside-contributor traffic that Jasper does not have. Nothing here blocks adding them later.
- **Preview deployments** (Web export on Pages, label-gated signed builds).
- **Rewriting the ledgers into issues.** The owner keeps `*-LEDGER.md`.

## 4. Anti-goals

These would make it a failure even if it technically works:

- **A green check that tested nothing.**
  - A skipped lane that should have run, a gtest filter matching nothing, or an MCP shard with zero files
    passes `Check`.
  - So `Check` treats "skipped" as success only when `changes` said so (§9). Every test step goes through the
    existing zero-test gates (`tools/ci/gtest-gate.py`, `run_tests.py` "no test ran").
- **A red check nobody can act on.** For example a link to a 40,000-line log, or a failure that does not
  reproduce with the printed command.
- **Flaky gates.** A wall-clock assertion or a race in CI teaches everyone to re-run until green.
  - Budgets go through `harness.over_budget` / `perfSlack()` (existing rule), and CI sets the runner's slack.
  - A flaky test is fixed or quarantined (`DISABLED_` plus an issue), never retried automatically.
- **A cache scheme that silently thrashes.** Ten lanes evicting each other's ccache would leave every build
  cold.
- **Secrets in PR jobs, `pull_request_target` running PR code**, or a release job that a PR can trigger.
- **CI that agents route around.** For example "merge with `--admin`", skipping the queue, or a
  `[skip ci]` habit.

## 5. Constraints

### 5.1 GitHub, public repository on an organization

Verified on 2026-11-12 against the docs (`docs.github.com/en/actions/reference/limits`, `…/github-hosted-runners`,
`…/product-billing/github-actions`, `…/github-packages`) unless marked:

| Limit | Value | Consequence |
|---|---|---|
| Standard runners | free, unlimited minutes | Windows and macOS run on every PR, not on demand |
| `ubuntu-latest` / `windows-latest` | 4 vCPU, 16 GB RAM, 14 GB SSD | builds stay at `-j4`; free disk first (§10.3) |
| `macos-latest` (M1) | 3 vCPU, 7 GB RAM, 14 GB SSD | slowest lane; arm64-only on PRs, universal on releases |
| `ubuntu-slim` | 1 vCPU, 5 GB; a 15-minute job cap that `timeout-minutes` cannot raise; an unprivileged container without Docker (secondary sources) | only `check` and the report renderer; `changes` runs on `ubuntu-latest` (§8.2) |
| Concurrent jobs | 20 in total, 5 macOS | at most 2 macOS jobs per run (§7) |
| Job time limit | 6 h | player builds are split per backend (§12) |
| Matrix | 256 jobs per run | no constraint |
| Actions cache | 10 GB per repo; LRU eviction; 7 days without use | the real squeeze (§10.2) |
| Cache scope | a run restores from its own ref and the default branch | merge-queue caches are invisible to PRs |
| Artifacts (public repo) | do not count toward storage (GitHub staff, community discussion #26438, 2020) | upload logs, goldens, screenshots freely; retention set per artifact |
| GHCR (`ghcr.io`) | public packages free to store and pull | build images live there (§10.1) |
| `GITHUB_TOKEN` API | 1,000 requests/h per repo | diffs come from git, not the REST API (t3code) |
| Merge queue | organization-owned repos only (secondary sources, consistent) | hence the move to the org |

no test suites. A failure there still reports (§11.4).

### 7.3 Concurrency, permissions, timeouts

- **Concurrency groups:**
  - PR: `ci-pr-<number>`, `cancel-in-progress: true`.
  - merge queue: `ci-mq-<ref>`, no cancel.
  - push: `ci-main-<sha>`, no cancel.
  - nightly and release: one group each, `cancel-in-progress: false`.
- **Merge queue settings** (owner's org ruleset):
  - build concurrency 1, group size up to 3, merge method "merge commit" (as `main`'s history uses today);
  - status-check timeout 180 min;
  - required check `Check`.
- **Permissions:**
  - `permissions: contents: read` at workflow level.
  - Escalation per job only: `packages: write` in `images.yml` and the push-to-`main` image step;
    `pull-requests: write` and `issues: write` in `ci-report.yml`; `contents: write` in the release jobs.
  - No workflow uses a secret other than `GITHUB_TOKEN`.
- **Timeouts:** every job sets `timeout-minutes` at about 1.5× its measured p95. No job relies on the 6 h
  default.
- **Action pinning:**
  - Third-party actions are pinned by full commit SHA with the version in a comment.
  - `actions/*` and `docker/*` are pinned the same way.
  - Dependabot bumps them weekly in one grouped PR, which CI itself checks.

## 8. Change detection (`changes`)

**Rule: CI does not get its own change detector.** `tools/check-changed` already maps a diff to builds, unit
gtest suites (through Ninja's include database) and MCP test files (through the coverage map). It is the
per-commit gate agents run, so CI planning the same way means "check-changed passed locally" predicts the PR
lanes.

### 8.1 Additions to `tools/check_changed.py`

1. **`--plan-json FILE`** writes the plan without running it:
   - `builds` (the existing names);
   - `unit` (`all` or `{core: [suites], editor: [suites], htmlui: [suites]}`);
   - `mcp` (`all`, `ci`, or a file list with a reason each);
   - `self_tests`, `modules_off`, `navigation_off`;
   - `fallbacks` (why anything widened).
   - It implies `--dry-run` and exits 0 on any plan; it exits 2 only when it cannot plan.
2. **`--deps-from DIR`** reads `ninja -t deps` dumps (`core-tests.deps`, `editor-tests.deps`,
   `htmlui-tests.deps`) from a directory instead of running Ninja in the image.
   - The `changes` job then needs no Docker and no build tree.
   - The dumps come from `main` (§10.2 "plan inputs").
3. The coverage map is found through the existing `JASPER_MCP_COVERAGE_MAP` variable, pointing at the map the
   nightly publishes.
   - Age limits (`MAP_MAX_AGE_DAYS=14`, `MAP_MAX_COMMITS=400`) stay as they are.
   - The `changes` checkout fetches enough history to count commits to the map's commit
     (`fetch-depth: 0` filtered with `--filter=blob:none`, which is cheap).

These are pure additions: the local default behaviour is unchanged. `tools/test_check_changed.py` gets cases for
both flags.

### 8.2 The `changes` job

Runs on `ubuntu-latest`, not `ubuntu-slim`: the slim runner's 15-minute cap is too tight for a blob-less
history whose diff against the map's commit fetches blobs lazily. It:

1. Checks out with blob-less full history, so the merge base and the map's commit resolve.
2. Restores "plan inputs" (deps dumps and coverage map) from the `main` cache.
3. Runs `check-changed --base <PR base sha> --plan-json plan.json --deps-from …`.
4. Turns the plan into job outputs:
   - per-lane booleans;
   - gtest filters;
   - an MCP shard matrix, made by `tools/mcp/shard.py plan`. Its `--tests` input is `run_tests.py --list` over
     the selected CI-suite files, and its `--timings` input is the per-test `mcp-test-seconds.json` (keys
     `file::test`) from the nightly. `shard.py` ignores per-file keys (`tools/mcp/shard.py:93-109`), so
     `mcp-file-seconds.json` is the wrong input. Shards hold about 20 min of recorded work each. Shard runs
     use `--plan`, which writes no file-seconds, so each shard uploads its test-seconds and the nightly merges
     them (`shard.py merge`).

**CI's lane rules on top of the plan.** These are stricter than the local plan, because "the engine not
building" is the top risk:

- **Platform build lanes:** `linux`, `windows`, `macos`, `ios`, `web` and `android` all run when the diff
  touches anything outside an explicit list of paths that neither the build nor any test reads:
  - the list: `docs/specs/**`, `docs/superpowers/**`, `docs/engine-gaps/**`, `docs/openengine-analysis/**`,
    `docs/test-cleanup/**`, root `*-LEDGER.md`, `README.md`, `.claude/**`;
  - everything else counts as building, including the rest of `docs/`. The editor embeds `docs/mcp/guide/**`
    and `docs/unity-glossary.md` (`CMakeLists.txt:391-394,497`), and tests read other docs
    (`CommandCatalogTest.cpp` reads `keyboard-shortcuts.md`; `EffectGuideTest.cpp`; `test_docs.py`);
  - `check-changed`'s `BUILDS_NOTHING` (`tools/check_changed.py:116`) is defined but unused, and too broad for
    this. The list above becomes a new constant beside it. A path joins it only with a note saying nothing
    reads it;
  - locally, check-changed builds web only for `engine/` code and Android only for its own platform code. That
    is right for a developer's machine and wrong for a gate.
- **`smoke`:** runs when the diff touches `engine/`, `editor/` (export, generator, stream, players),
  `tools/smoke-test.sh`, `tools/fixtures/**`, `editor/resources/templates/**` or the root CMake.
  - That is the `COMPILE_PATHS` and `SAVED_OUTPUT_PATHS` families check-changed already names, plus templates.
- **MCP selection:** a planned file that is not in the CI suite (needs the fixture, or `CI_EXCLUDED`) is left
  out. The report lists it under "not run in CI".
- **Fail-open rules:**
  - A plan error, a missing deps dump or a missing map means the full set for that lane, with the reason in
    the report.
  - A `.github/**` change runs everything.
- **merge_group, push to `main`, and `workflow_dispatch` with `full: true`** skip planning: everything runs.

## 9. The `Check` job

Runs on `ubuntu-slim` with `if: always()`; `needs` lists every other job.

- It passes only when every needed job is `success`, or is `skipped` *and* `changes` said that lane was not
  needed. As in t3code, it uses `toJSON(needs)` and `jq`.
- `always()`, not `!cancelled()`, because a cancelled run must still report a failing check.
- It also fails when:
  - a test lane reported zero tests (from its report JSON, §11.1);
  - an MCP shard ran zero files;
  - the merge-queue or full run skipped any lane.
- **Skipped tests.** A skipped MCP test fails its shard unless its file and test are listed in
  `tools/ci/mcp-allowed-skips.txt`, with the reason and the lane where it does run. For example,
  `test_mesh_raycast.py::test_web_latency` needs the mesh-raycast web build, so it runs in the nightly, which
  builds it.
  - This is the CI form of the local rule "a test check-changed selected that skips fails it"
    (`tools/check_changed.py:774-786`).
  - Adding an entry is a reviewed change in a PR, like any other.
  - gtest keeps `--max-skipped 0` and its existing HTML UI allowance.
- **Ruleset** (owner, on the org repo):
  - require a PR, require `Check` from the GitHub Actions app, require the merge queue;
  - block force-push and deletion of `main`;
  - **no bypass list.** In an emergency the owner disables the ruleset by hand, which is visible and
    deliberate.
  - Agents use the owner's `gh` credentials, so a bypass list would let an agent merge red. `AGENTS.md` forbids
    `--admin` either way.

## 10. Images, caches, disk

### 10.1 Build images on GHCR

- **Names:** `ghcr.io/<owner>/jasperengine-<target>-build:<hash>`, where `<hash>` is the same 12-hex content
  hash `tools/build.sh` computes, plus `:latest`. The hash function moves into one place:
  `tools/build.sh image-tag <target>` prints it, and both CI and the local build use it.
- **Images:** `linux`, `web`, `android`, `linux-backends` and `runtime` (`docker/runtime.Dockerfile`,
  ubuntu:24.04, which the prebuilt smoke uses, `tools/smoke-test.sh:103`).
- **The `linux-backends` hash chains:** it is `FROM jasperengine/linux-build`, an unversioned local tag, and is
  built without a hash today (`tools/build.sh:208`, `tools/smoke-test.sh:108`). Its tag hashes its own
  Dockerfile plus the `linux` image's hash, and its `FROM` takes the base by that hash (a build arg), so a
  change to the base rebuilds it.
- **Who pushes:** `images.yml` on `main` when `docker/**` changed, weekly (base image and apt drift, as Doriax
  does with Nix), and on dispatch.
  - It uses `docker/build-push-action` with `cache-from`/`cache-to: type=registry` on a `:buildcache` tag.
  - It never uses `type=gha`.
- **How lanes get the image (the `image` action):**
  1. Compute the tag.
  2. `docker pull` it if it exists, then pass it as `JASPER_DOCKER_IMAGE`.
  3. Otherwise build it locally with the registry cache as `cache-from`. This happens on a PR that changes
     `docker/**` before `images.yml` has run.
  - PRs never push. A fork can then never write packages.
- **Package settings:** visibility public, linked to the repository. Untagged versions older than 30 days are
  deleted by the weekly run.

### 10.2 The Actions cache: 10 GB, budgeted

**What is cached and who writes it:**

| Entry | Writer | Size cap (initial; measure in rollout) |
|---|---|---|
| `ccache-linux-<imagehash>` | push to `main`, `linux` | 1.5 GB |
| `ccache-unit-<imagehash>` | push to `main`, `unit` | 1.5 GB |
| `ccache-asan-<imagehash>` | push to `main`, `asan` | 1.5 GB |
| `ccache-htmlui-<imagehash>` | push to `main`, `htmlui` | 0.8 GB |
| `ccache-web-<imagehash>` | push to `main`, `web` | 0.8 GB |
| `ccache-android-<imagehash>` | push to `main`, `android` | 0.8 GB |
| `ccache-windows-<msvc version>` | push to `main`, `windows` | 1.2 GB |
| `ccache-macos-<xcode version>` | push to `main`, `macos` | 0.8 GB |
| `plan-inputs` (deps dumps) and `mcp-timings` | push to `main` / nightly | < 50 MB |
| `coverage-map` | nightly | < 100 MB |
| tool downloads (Vulkan SDK, Gradle) | their lanes, on `main` | < 0.5 GB |

That totals about 9.5 GB, inside 10 GB.

**Rules:**

- A PR or merge-queue run uses `actions/cache/restore` only. Push to `main` and nightly save with
  `actions/cache/save`.
- The key is `<entry>-<run_id>`; restore uses the `<entry>-` prefix.
- After a save, the job deletes older entries of the same prefix (`gh cache delete`, `actions: write` on that
  job only), so each entry has exactly one live copy and LRU never evicts one lane on behalf of another.
- A save is skipped when ccache's stats show no new entries.
- The cap is `CCACHE_MAXSIZE`, forwarded by `tools/build.sh`.
- Nightly lanes (TSan, unity, Vulkan and the others) restore the nearest ccache but never save. They are
  allowed to be cold.
- **If rollout measurement shows the table cannot fit** (for example the unit and asan trees compress worse
  than estimated), the fallback is to store each lane's ccache tarball as an OCI artifact in GHCR (`oras push`,
  free for a public package) instead of the Actions cache.
  - Which entries move is decided by measurement, recorded in `docs/testing.md`.
  - The fallback stays unbuilt unless needed.

### 10.3 Disk

The `free-disk` action runs first on every Linux job that pulls an image. It removes the runner's preinstalled
Android SDK, .NET, GHC, CodeQL bundle and unused Docker images. Common practice frees 20–30 GB; this is to be
measured, not taken from docs.

- **Job layout:**
  - Linux jobs keep only what they need: image, checkout, build tree, ccache.
  - Windows jobs build on `D:` when the runner provides it.
  - Each job prints `df -h` at its end into the report, so a disk regression shows up before it fails.

## 11. The failure report

### 11.1 Collection: `tools/ci/report.py`

A new script, the only new Python of this design besides the check-changed flags. It runs in every lane as its
last step (`if: always()`, through the `report` action). It reads that lane's existing outputs:

- **gtest XML** (`build/test-results/*.xml`): the failed test names, `file:line` and the failure message.
- **`mcp.json`:** failed or crashed tests, `detail`, `left_out`.
- **Build logs** (`build/test-results/*-build.log`; MSVC and Xcode logs on their lanes): the first 20 diagnostics
  matching `error:`, MSVC `error C####`/`LNK####` and ld `undefined reference`, each with `file:line` and three
  lines of context. Paths are made relative to the repository.
- **Smoke:** the failed step and the tail of its log.
- **Gate outputs:** the web gate transcript and `gtest-gate.py` messages.

It writes two things:

- `build/test-results/ci-report/<lane>.json`:
  - `{lane, status, sha, commands[], failures[{kind, title, location, excerpt, repro}], tests{ran, failed, skipped, disabled}, artifacts[], timings{}, disk}`
- A Markdown block appended to `$GITHUB_STEP_SUMMARY`.

**The `repro` of a failure is the lane's command narrowed to it.** For example:

- `UNIT_SUITE=core UNIT_TEST_ARGS='--gtest_filter=MeshBvh.Refit' WERROR=1 tools/build.sh unit-tests`
- `MCP_TEST_ARGS='-k test_undo_paint' tools/build.sh mcp-tests tools/mcp/tests/test_tileset.py`
- `tools/ci/windows.sh editor`

Each lane declares its base command once, in its YAML `env`, which `report.py` reads. The repro is the command
CI ran, not a guess.

Report artifacts are uploaded per lane (`ci-report-<lane>`, 14-day retention), next to the evidence the old
workflows already uploaded:

- `test-results-*` (always);
- golden diffs and smoke PNGs and logs (on failure);
- `editor.log` (on failure).

### 11.2 The PR comment

`ci-report.yml` runs on `workflow_run` (`completed`) from the default branch's copy of the workflow, so a PR
cannot change what writes to it. It:

- downloads the `ci-report-*` artifacts and treats them as untrusted data: JSON parsed with size limits, text
  Markdown-escaped and fenced;
- finds the PR (from `workflow_run.pull_requests`, or the `gh-readonly-queue/main/pr-<N>-…` ref for a
  merge-queue run);
- upserts one comment, marked `<!-- jasper-ci-report -->`.

Layout while red:

```text
❌ CI failed on 3f2c1ab — 2 of 14 jobs                      run #812 · 47 min

windows — Windows MSVC editor build
  error C2027: use of undefined type 'jasperengine::Transform'
    editor/window/InspectorTerrain.cpp:412
      410 |   auto& t = scene->getComponent<Transform>(e);
  Reproduce (Windows, x64 Native Tools shell):  tools/ci/windows.sh editor
  Logs: windows-build.log

mcp (3/6) — 1 failed, 214 passed, 0 skipped
  test_tileset.py::test_undo_paint
    expected 3 tiles after undo, got 4
  Reproduce:  MCP_TEST_ARGS='-k test_undo_paint' tools/build.sh mcp-tests tools/mcp/tests/test_tileset.py
  Evidence: editor.log, screenshots

Passed: changes · lint · linux · unit (412 tests) · htmlui (skipped: no HTML UI change) · …
```

- **Layout when green:**
  - The comment collapses to one line: "✅ CI passed on 3f2c1ab: 14 jobs, 52 min".
  - Then a `<details>` block with per-lane test counts and the skipped lanes with their reasons.
- **Size:** a GitHub comment holds 65,536 characters. The renderer gives each failure at most 40 lines and
  links the rest.
- **Staleness:** the header names the commit, so a stale comment is visible. A push does not touch the comment
  until its run completes.

### 11.3 Merge-queue failures

The queue removes the PR. `ci-report.yml` posts the same report on that PR, prefixed "Removed from the merge
queue:". The commit it names is the queue's merge commit; the PR's own head may be green, and the cause is then
an interaction with another queued PR.

### 11.4 `main` and nightly failures

A push-to-`main` failure, or a nightly failure, opens or updates one issue labelled `ci-red` (main) or
`nightly`. It uses the reporter of the old `nightly.yml`, extended to include the rendered report.

On a push-to-`main` failure, the PR that produced the commit (found via the commits/pulls API) also gets a
comment linking the issue.

### 11.5 Agent access

- `gh pr checks <N> --watch` blocks until checks finish. It is one command, not a polling loop.
- `gh pr view <N> --comments` shows the report.
- `gh run download <run> -n ci-report` gives the JSON.

`AGENTS.md` says exactly this (§13).

## 12. Releases

### 12.1 Channels and versions

- **Nightly:**
  - `nightly.yml` calls `build-release.yml` with `channel: nightly` when `main`'s head differs from the
    commit of the newest `nightly-*` release.
  - It skips when `main` has not moved, and it takes no other gate. Every commit on `main` already passed the
    merge queue's full set; slow-lane failures go to the `nightly` issue and do not withhold the download.
  - **Tag** `nightly-YYYYMMDD`, a prerelease, never "latest".
  - **Version stamp** is the tag itself, passed as `JASPERENGINE_EDITOR_VERSION=nightly-YYYYMMDD`
    (`CMakeLists.txt:26-57` accepts an override). The editor's player download takes its version as the release
    tag (`editor/players/PlayerRuntimes.cpp:370-373`).
  - **Today's editor refuses nightly downloads:** `isReleaseEditor()` accepts only `^v\d+\.\d+\.\d+$`
    (`:199-202`), so a nightly or `git describe` stamp counts as a development editor and refuses to download
    players. Phase 6 extends it to `nightly-\d{8}`, with a unit test. Nightly editors then download their own
    nightly's players, hash-checked like a stable's.
  - **Retention:** nightlies older than the newest 14 are deleted, release and tag.
- **Stable:**
  - `release.yml` takes `version`, validated `^v\d+\.\d+\.\d+$`: three parts only, because an editor stamped
    `vX.Y` refuses downloads (`isReleaseEditor`). `check-release-tag.sh` still accepts `vX.Y`, for the old
    tags. It also takes an optional `commit`.
  - `commit` defaults to the newest nightly's commit, so stable ships what nightly users already ran. It must
    be an ancestor of `main`.
  - The workflow creates the tag on that commit, runs `tools/ci/check-release-tag.sh`, then calls
    `build-release.yml` with `channel: stable`.
  - Which number comes next is the owner's choice when dispatching. The newest tag, `v0.7.1`, continues
    Doriax's line.

### 12.2 `build-release.yml`

Order, as the old `ci.yml` had it (the editor of a release embeds its players' SHA-256 values,
`tools/players/write_hashes.py`):

1. **Players, as a matrix split per platform × backend** (and per variant when one job would pass 3 h). The
   old single jobs had 300–360 min timeouts. Each job runs one script:
   - Linux: `PLAYER_BACKENDS=<one> tools/build.sh players`.
   - Web: `PLAYER_PLATFORM=web tools/build.sh players`.
   - Android: `PLAYER_PLATFORM=android tools/build.sh players`.
   - Windows: `tools/ci/players-windows.sh <backend>` (new; the old inline loop moved to a script).
   - Apple: `tools/ci/players-apple.sh <macos-backend|ios>` (new, likewise).

   Flavours: `release` for nightly; `release development` for stable. Every variant of `engine/player/variants.json`.
2. **`player-hashes`** writes `editor/players/PlayerRuntimeHashes.gen.h`. It fails unless every player job
   succeeded.
3. **Editors**, with the hashes header:
   - **Linux:** in the Linux build image (it is `ubuntu:22.04`, the glibc floor Doriax and S02 D6 chose), then
     the AppImage plus zsync step of the old workflow. The old separate bare-`ubuntu:22.04` container job is
     dropped: one Linux toolchain, not two.
   - **Windows:** MSVC through `tools/ci/windows.sh package`.
   - **macOS:** universal, ad-hoc signed (`codesign --sign -`, required for arm64), zip plus dmg through
     `tools/ci/macos.sh package`.
4. **Launch checks:**
   - The editor has no `--version` option, and `jasperengine-editor-cmd` exists only on Windows
     (`CMakeLists.txt:2066-2090`).
   - **Linux:** in the Linux image, the AppImage (`APPIMAGE_EXTRACT_AND_RUN=1`) runs `call --help`, then
     `call --project <scratch copy of a fixture> editor_status` under Xvfb. That is a one-shot headless editor,
     which opens a project.
   - **macOS:** the zip runs `tools/ci/check-call-cli.py`.
   - **Windows:** the zip runs `tools/ci/check-call-cli.py` against `jasperengine-editor-cmd`.
   - Prebuilt end to end: the existing `prebuilt` and `prebuilt-android` jobs, against the packaged players.
5. **Publish:**
   1. Download all artifacts with `merge-multiple`.
   2. Write `SHA256SUMS` from the final files.
   3. Create the release as a **draft**, upload everything with `--clobber`, then un-draft.
   4. Body: GitHub's generated notes plus a fixed "Opening unsigned builds" section (§12.5).

## 14. Development plan

This plan follows the rules it introduces, so it is fast and checkable as it goes.

### 14.1 Phases

Each phase is one PR, in a worktree on its own branch, and is checked by the CI of the phases before it:

| Phase | Lands | Proves it with |
|---|---|---|
| 0 | `changes` (`--plan-json`, `--deps-from`), `lint`, `check`, `report.py`, `ci-report.yml`, PR template, CONTRIBUTING, `AGENTS.md` Pull requests section; ruleset requiring `Check` (no queue yet) | the red-control PR (14.2) shows a lint failure in the comment; then green |

Phases 1–3 can be worked in parallel worktrees once phase 0 lands. They touch separate jobs and scripts.

### 14.2 The red control

CI's own behaviour claims need a run that fails. A long-lived draft PR `ci/red-control` (never merged) carries
one deliberate breakage per lane. Each phase:

1. Pushes the breakages for its lanes.
2. Links the red run and its report comment in the phase PR.
3. Reverts them.

### 14.3 Speed rules for building it

- **Copy before writing:** start every job from the old workflow's step, diff it against today's scripts, keep
  what still holds.
- **Logic in scripts, never in YAML:** each new script runs locally first (`bash -n`, a local run where the OS
  allows), and only then in CI.
- **Lint the workflow before pushing:**
  - `actionlint`, pinned, also in the `lint` lane;
  - `act` is not used: it does not match the hosted runners closely enough to be evidence.
- **Iterate on one lane:** `workflow_dispatch` with a lane filter is not added. Instead, push to the phase PR
  and read the report. The cancel-in-progress group keeps it to one run.
- **Measure, then tune:** caps, shard size and timeouts start from this document's numbers and are corrected
  from the first ten runs, then recorded in `docs/testing.md`.

## 15. Acceptance criteria

1. **AC1 — gate.** `main`'s ruleset requires `Check` and the merge queue, and has no bypass actors. Shown by
   `gh api` output in the phase-4 PR.
2. **AC2 — no silent green.**
   - On the red-control PR, each of these turns `Check` red: a skipped needed lane, a gtest filter matching
     nothing, a zero-file MCP shard and a cancelled run.
   - A docs-only PR is green with every build lane skipped, and the reason is shown.
3. **AC3 — every platform build gates.** The red control has one compile error visible to only one of: GCC,
   MSVC, Apple Clang (macOS), Xcode iOS, Emscripten, Android NDK. Each turns its lane and `Check` red, and only
   that lane.
4. **AC4 — games build.**
   - **Linux:** `smoke` exports and launches `tools/fixtures/post-processing` (compile) and
     `tools/fixtures/unified-lighting` (prebuilt), plus a project created from each template in
     `editor/resources/templates/`.
   - **Windows and macOS:** a Compile build of `tools/fixtures/post-processing` succeeds.
   - A broken fixture turns `smoke` red.
5. **AC5 — the report.** For each red-control failure, the PR comment names the job, the failing
   `file:line` or test, the excerpt, and a repro command. Running that command locally reproduces the failure
   (Linux lanes, verified by the implementer). The comment collapses to one line when green.
6. **AC6 — PR timing.** Over the first 20 PRs after phase 3, record p50 and p95 from push to `Check`. Target:
   ≤ 60 / ≤ 120 min warm. A miss is recorded in `docs/testing.md` with the slowest lane named, not hidden.
7. **AC7 — queue timing.** A merge-queue group takes ≤ 120 min (measured).
8. **AC8 — cache.** After a week, the Actions cache holds exactly one entry per §10.2 row and stays under
   10 GB (`gh cache list`). A PR's `linux` lane reports a ccache hit rate ≥ 80% on a one-file change.
9. **AC9 — nightly.**
   - A scheduled run on an unchanged `main` publishes nothing.
   - After a merge, it publishes `nightly-YYYYMMDD` with every §12.3 asset and a `SHA256SUMS` that matches.
   - A forced slow-lane failure updates the `nightly` issue.
10. **AC10 — stable.** `release.yml` with `dry_run: true` on a real three-part version:
    - runs everything up to a complete draft, including every launch check, and never un-drafts;
    - its editor installs the release's player zips from disk (`players install <zip>`, hash checked against
      the embedded table), and refuses a zip whose hash differs;
    - the draft is deleted afterwards, so it never becomes "latest" for zsync.

    The download path itself is proven by AC9's nightly, whose editor downloads its own players.
11. **AC11 — security.**
    - No workflow uses `pull_request_target`; `ci-report.yml` is the only `workflow_run`.
    - No job has more than its listed permissions.
    - Every action is pinned by SHA (`actionlint` plus a grep in `lint`).
12. **AC12 — docs.** `AGENTS.md`, `docs/testing.md`, the PR template and CONTRIBUTING describe the workflow as
    built. `tools/check_agent_docs.py` passes.

## 16. Risks and open items

1. **Cold builds.** The first build after an image change, and every nightly-only config, is cold on 4 vCPUs.
   An editor plus engine cold build is not measured on a 4-vCPU runner; the build servers are larger. If a cold
   `linux` lane passes 90 min, the fallback is to split the editor and the engine sample project into two jobs.
2. **MCP shards and llvmpipe.**
   - Shards run `-j 2` on 4 vCPU with `LP_NUM_THREADS` per the existing table.
   - If the CI suite needs more than 8 shards at about 20 min, the merge-queue run uses up to 12 shards. It
     still fits 20 concurrent jobs with the other lanes staggered.
3. **PR evidence.** `gh` has no attachment upload. The candidate `tools/ci/pr-evidence.sh` uploads images as
   assets of a rolling `pr-evidence` prerelease and prints Markdown links.
   - Whether release-asset images render inline in a PR body is unverified.
   - If they don't, links are the fallback, and `AGENTS.md` says so.
4. **Windows and macOS Compile builds headless.** Exporting and compiling a fixture needs the editor
   headless on a runner with no GPU. Linux uses Mesa in the image; Windows and macOS have none.
   - If the headless editor needs a GL context there, the lane instead generates the project with the editor
     CLI and builds it with the generated CMake and the same compiler. That is the same compile path as
     Export > Compile.
   - The implementer verifies which one works; AC4 holds either way.
5. **Merge queue on an organization.** Done: the repository is `Arakuma-Studio/JasperEngine` (2026-11-12).
