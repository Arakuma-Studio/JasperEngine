# Version control

The editor works with the Git or Subversion checkout a project lives in: it shows what changed
and who locked what in the Project window, the Hierarchy and the Inspector, commits, reverts
(undoably), locks binary assets, diffs scenes GameObject by GameObject and merges them
(docs/specs/S29-version-control.md). Agents use the same features through MCP:
`jasper://docs/vcs` (docs/mcp/guide/vcs.md).

## Setting up

- Install Git (2.30 or newer) and, for locks, Git LFS (3.0 or newer), or Subversion (1.10 or
  newer). The editor runs the installed programs; it finds them on `PATH` (and on macOS in
  `/usr/local/bin`, `/opt/homebrew/bin` and `/usr/bin`), never in the project folder. Preferences >
  Version Control can name each executable.
- Open a project inside a checkout: the editor looks for `.git` or `.svn` from the project folder
  up. Project Settings > Editor > Version Control picks Auto (default), Git, Subversion or None.
  The status bar shows the branch, commits ahead (↑) and behind (↓), the changes, and the last
  error; it says "Version control: not available (...)" when the programs are missing, and the
  editor works as without version control. A detached HEAD shows its tag ("tag v1.2", tag icon)
  or its short commit (commit icon). An operation left unfinished shows in git's prompt words, in
  amber: "main | MERGING", "feature | REBASE 2/5", "| CHERRY-PICKING", "| REVERTING",
  "| BISECTING"; conflicts show as "2 conflicts" in red, and a click then opens the Conflicts
  window instead of Commit. The tooltip splits the changes into staged, modified, untracked and
  conflicted and says how to finish the operation.
- Credentials are yours: the editor never shows a password prompt (it runs git with
  `GIT_TERMINAL_PROMPT=0`), so use a credential manager or SSH keys. A remote that asks for a
  password fails with git's message.
- New projects get Git LFS and lockable binary assets in their `.gitattributes` (Project Settings
  > Editor > Version Control > Git LFS; existing projects keep their binaries out of LFS until
  you turn it on). Lockable Scenes adds scenes and prefabs to the lockable files.
- The editor keeps `.gitignore` and `.gitattributes` up to date (Project Settings > Editor >
  Version Control Files): it rewrites the lines from its "Generated by JasperEngine Editor." first
  line down to its "End of the JasperEngine Editor's lines" line. **Add your own lines below that
  line**: they are kept as you wrote them. Git reads later lines last, so a line of yours there
  overrides the editor's (`!build/` ignores `build/` no more; `*.png -lockable` unlocks PNGs). A
  file without the first line is yours and never rewritten (turning Version Control Files off
  leaves both files alone). Files of older editors, which had no end line, keep the lines you
  added once, below the new end line.
- **Smart Merge**: Preferences > Version Control > Set Up Smart Merge registers the editor as the
  repository's merge driver for scenes and prefabs (`git config merge.jasperengine-scene.driver`).
  Each clone sets it up once; the status bar's tooltip says "Smart merge: not set up" until then.

## What changed

- **Project window**: a glyph at the bottom-left of each thumbnail (before the name in list
  view): amber pen modified, green plus added, grey question mark untracked, red deleted, red
  triangle conflicted, green lock locked by you, red lock locked by someone else, blue arrow the
  server has a newer version. Folders show the strongest state inside them. The tooltip names the
  state and the lock's owner. An asset and its `.meta` count as one file.
- **Hierarchy**: the scene row shows its file's state. With Show VCS Changes on (the branch
  button in the Hierarchy toolbar), each GameObject added, modified, reparented or reordered since
  the last commit has a glyph after its name, unsaved edits included (the diff follows your edits
  half a second after the last one).
- **Inspector**: a 2-px amber bar at the right edge marks each property that differs from the
  last commit; its tooltip is "Baseline: <value>" and its context menu has Revert to Baseline and
  Copy Baseline Value. A component's menu has Revert Component to Baseline. Each revert is one
  undo step ("Revert transform.position to Baseline"), so Ctrl+Z brings the edit back.
- **Code editor**: lines changed since the last commit (HEAD; Subversion: BASE) are marked in the
  gutter between the line numbers and the text: a green bar for added lines, an amber striped bar
  for changed ones, a red triangle where lines were removed; the same marks are in the left third
  of the vertical scrollbar. Hover a mark (or click it, which keeps it open) for the old lines and
  the new ones, highlighted, with the changed characters tinted; its buttons go to the previous
  or next change and Revert Change puts the old lines back (one undo step: Ctrl+Z brings your
  edit back). The context menu has Revert Change (at the caret), Next Change (Alt+F5) and
  Previous Change (Shift+Alt+F5). The status row under the tabs says "3 changes" (its menu: Next
  and Previous Change, Show Diff, Show History, Revert File...), or why a file has no marks: New
  file, Untracked, Ignored, Outside the repository, Not compared (binary, a Git LFS file, over 4
  MiB). The marks follow your edits as you type, unsaved ones included; a CRLF checkout of an LF
  file shows no false changes, and a renamed file compares with its old path. Preferences >
  Version Control > Show Changes in Code Editor turns them off (no version control process runs
  for them then).
- **Scene Diff** (Window > Version Control > Scene Diff): the tree of GameObjects, components and
  properties that differ, against the baseline (HEAD; Subversion: BASE) or a revision from
  History. Changed Only filters; a click selects the GameObject; each row has Revert to Baseline.
  Values the engine computes on load (world matrices) are never differences, and reordering a
  script's properties is not a change.
  A scene too big to encode within the frame budget shows its saved changes instead ("Showing
  saved changes").
- Version control is read every 10 seconds, at once after a save or a version control operation,
  and when the editor regains focus; locks every 60 seconds (Preferences > Version Control
  changes both). Assets > Version Control > Refresh Version Control reads both now.

## Committing, reverting, history

- **Assets > Version Control** (also in the Project window's and the Hierarchy's context menus):
  Commit..., Revert..., Lock, Unlock, Show History, Diff Against Baseline, Refresh. A disabled
  item's tooltip says why.
- **Commit** window (Window > Version Control > Commit, or a click on the status bar): check the
  files to commit (filter, status column; double-click a file for its text diff, or for a scene
  or prefab its Scene Diff), write the message (the hint marks a first line over 72 characters)
  and Commit. Only the checked files go in, whatever else is staged; an asset's changed `.meta`
  goes along. Unsaved checked scenes are saved first ("Save and Commit"). Commit and Push pushes
  after the commit (Git; remembered). Progress, Cancel and git's output are in the window and the
  Console; hooks run.
- **Revert...** discards the selected files' changes, `.meta` included. It is one undo step
  ("Revert 2 files"): Edit > Undo restores your changes byte for byte. An open scene whose file
  changed reloads; one with unsaved edits asks first. New files cannot be reverted: delete them.
- **History** (Show History, or Window > Version Control > History): revision, author, date and
  message, 100 at a time (Load More). For a file: Diff with Working Copy (a scene opens the Scene
  Diff against that revision) and Copy Revision.
- Fetch, Pull (fast-forward only) and Push run in the background; nothing blocks the editor.

## Locks

Binary assets (and scenes, with Lockable Scenes) can be locked so no one else edits them: Git
LFS locks or Subversion's `svn:needs-lock`.

- Lock and Unlock in the menus; the Inspector of a lockable asset or an open scene shows a banner:
  "Not locked" with Lock, "Locked by you" with Unlock, or "Locked by <owner> — read only", which
  makes the Inspector read-only until you press Edit Anyway.
- **Lock on Edit** (Preferences > Version Control): Ask (default) asks "Lock <file>?" (Lock / Edit
  Without Lock / Cancel, which undoes the edit) when your first edit dirties a lockable scene or
  changes a lockable asset's import settings; Auto locks in the background and says so when it
  fails; Off never asks. A file locked by someone else always warns first.
- A save refused because the file is read-only (LFS and needs-lock checkouts) offers Lock and
  Save, or Make Writable and Save.
- Unlocking someone else's lock is forced and asks first: tell them.

## Conflicts

- With Smart Merge set up, `git merge` (or `git pull`, `git rebase`) merges scenes and prefabs
  GameObject by GameObject: edits to different GameObjects or properties merge cleanly, a
  GameObject both branches added with the same id is renumbered (and references to it follow).
  Real conflicts (the same property changed differently, a GameObject deleted on one side and
  edited on the other) keep your version in the file and are listed in
  `.jasperengine/merge/<path>.conflicts.yaml`; git marks the file unmerged.
- Without Smart Merge git merges the text, and a conflict leaves `<<<<<<<` markers in the scene,
  which no loader reads: set it up before merging branches that edit scenes.
- **Conflicts** window (Window > Version Control > Conflicts): for a scene or prefab, Smart Merge
  merges the three versions git (or Subversion) kept, then each remaining conflict takes Ours or
  Theirs; Mark Resolved writes the file and marks it resolved. Other files offer Use Ours, Use
  Theirs or Open in External Tool. A conflicted scene does not open until it is resolved.
- From a terminal: `jasperengine-editor scene-diff <old> <new> [--json]` diffs two scene files;
  `merge-scene <base> <ours> <theirs> <path>` is the merge driver itself (exit 0 merged, 1
  conflicts, 2 unreadable input).

## Subversion

The same features, with Subversion's names: Commit commits the checked files (new ones are
added first), Revert reverts, Pull is Update (conflicts are postponed to the Conflicts window),
Fetch and Push do not exist. Locks are Subversion locks on `svn:needs-lock` files; the Conflicts
window reads the `.mine`/`.rOLD`/`.rNEW` files. The baseline is BASE, the revision checked out:
HEAD given anywhere (the Scene Diff, Diff Against Baseline, the tools) reads BASE, so another
user's newer commit never shows as a change of yours; a revision number compares with that
revision. A file added with `svn add` has no BASE (the Scene Diff lists all of it as added); a file
moved with `svn move` compares with the file it was moved from. A working copy of `^/tags/<tag>`
shows its tag in the status bar.

## Checking it by hand

The automated tests cover the providers, the diff, the merge and the tools
(`editor/tests/vcs/`, `tools/vcs-tests/merge_driver_test.sh`, `tools/mcp/tests/test_vcs.py`).
What they cannot see is checked by hand on Linux and Windows:

1. In a Git project (`git init`, commit everything), edit a scene: move a GameObject. The
   Hierarchy shows the amber glyph after its name and the Inspector the amber bar on Position.
2. Right-click Position > Revert to Baseline: both go away. Ctrl+Z: both come back.
3. With Git LFS and a lock server (any LFS host, or `tools/vcs-tests/fake_lfs_lock_server.py`
   with `git config lfs.url http://127.0.0.1:<port>/alice`), select an `.fbx` in the Project window
   and Assets > Version Control > Lock: a green lock.
4. In a second clone (`lfs.url .../bob`), Refresh Version Control: the `.fbx` shows the red lock,
   and selecting it shows "Locked by alice — read only" in the Inspector.
5. Make a local bare remote (`git init --bare ../remote.git`, `git remote add origin ../remote.git`,
   `git push -u origin HEAD`), change two files, and commit them in the Commit window with Commit
   and Push checked. History shows the commit first, and `git -C ../remote.git log -1` has it.
