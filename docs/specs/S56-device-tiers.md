# S56: Device tiers, thermal and memory signals, upload pacing

Wave 5. Research: `docs/forge-meshopt-analysis/forge-architecture.md` (§1 top five, §4.12, the GPU
config sections). The Forge clone's data: `Common_3/OS/*/..._gpu.data`.

## 1. Goal

Games run well on the whole range of phones and browsers without each developer hand-tuning. At
startup the player identifies the GPU, picks a Device Tier, and applies that tier's quality
overrides. While running it reacts to thermal and memory pressure: it lowers render scale and frame
rate before the OS throttles or kills the app. It also spreads texture and buffer uploads so
streaming does not hitch. Developers see and override all of it in the editor, simulate any tier in
the Game view, and agents can read and set it.

## 2. Scope

In scope:
- **GPU database:** Low, Medium, High and Ultra tiers per platform, from The Forge's `gpu.data`
  tables converted to our JSON, plus our own rules.
- **Device Tier overrides** in Project Settings > Quality, with Game view simulation.
- **Thermal and memory signals** on Android, iOS and web, feeding dynamic resolution (S13), a frame
  rate cap and texture streaming.
- **A per-frame upload byte budget** in the sokol command queue.
- **Editor, Lua and MCP surfaces.**

Out of scope:
- A full Unity-style Quality Levels system that rewires every setting. Tiers override a curated
  list of existing settings.
- On-device shader reload and a device farm: noted for later.

## 3. Current state

- **Signals:** there is no thermal or memory-pressure signal anywhere (`forge-architecture.md`
  §4.12).
- **Uploads:** `SokolCmdQueue.cpp:80,125` runs MAKE_IMAGE and UPDATE_IMAGE with no byte budget,
  and S32's `mainThreadBudgetMs` covers shaders only.
- **Quality:** settings are per-platform rows in Project Settings (`ProjectSettingsWindow.cpp`),
  with no per-device adaptation.
- **Device identity:** S13 dynamic resolution exists, and the GPU name is available
  (`sgj_device_name()` per the report; verify).

## 4. Reference

- The Forge `Common_3/OS/Android/android_gpu.data`, `OS/Darwin/apple_gpu.data` and
  `OS/Windows/pc_gpu.data` (Apache-2.0): copy the data and rewrite the parser.
  - Don't copy `GraphicsConfig.cpp`, which is too entangled.
  - Don't copy its unknown-GPU behaviour, which gives a NULL renderer.
  - Its Android ratings are calibrated for the visibility buffer, so treat them as relative
    order and re-map.
- Android `PowerManager.addThermalStatusListener` and `getThermalHeadroom` (API 29/30+),
  `ComponentCallbacks2.onTrimMemory`. iOS `NSProcessInfo.thermalState` and
  `didReceiveMemoryWarning`. Web: `navigator.deviceMemory`, the WebGL renderer string
  (`WEBGL_debug_renderer_info`) and `performance.memory` where present.

## 5. Requirements

### Functional

- **R1. GPU database** `engine/core/device/gpu_tiers.json`, generated by
  `tools/device/convert_forge_gpu_data.py` from the Forge files and our own overrides:
  - Entries match on vendor, a device id where available, and a case-insensitive renderer-name
    pattern (Android GLES and WebGL have no PCI ids).
  - Each maps to Low, Medium, High or Ultra.
  - Ordered rules: an exact name, then a family pattern (`Adreno (TM) 6[0-4]\d`), then a vendor
    default.
- **R2. Detection at startup** (player and editor):
  - Inputs: renderer name, vendor, backend, the platform's RAM and CPU core count.
  - **Unknown GPUs** get a heuristic tier from memory and cores: Android under 3 GB is Low, under
    6 GB Medium, otherwise High; iOS by device RAM; desktop High; web Medium, or Low under 4 GB
    `deviceMemory`.
  - It never fails, and the reason is logged ("Adreno 650, rule family, tier Medium").
- **R3. Device Tier overrides**, in Project Settings > Quality > Device Tiers:
  - A table of the curated overrides, one column per tier, per platform group: Render Scale,
    MSAA, Shadow Quality, Shadow Distance, LOD Bias (S54), Lit Quality, Texture Quality (mip
    bias or max size), Post FX toggles (bloom, SSAO, volumetrics), Target Frame Rate, Max Pixel
    Lights and Particle Budget.
  - An empty cell inherits the project value.
  - **Defaults:** Low halves render scale, uses Low shadows, LOD Bias 0.5 and no volumetrics or
    SSAO. Medium uses 0.85 scale. High and Ultra are the project values.
  - Edits are undoable.
- **R4. Overriding the tier:** players accept `--device-tier=<tier>` and a Lua
  `Device.setTier(tier)` at runtime. Games can expose a graphics menu with it.
- **R5. Game view simulation:** a Game view toolbar entry "Device: Auto | Low | Medium | High |
  Ultra", plus a platform family, applies the tier's overrides in Play. It is shown in the
  toolbar and the Stats overlay.
- **R6. Thermal state.** States are Nominal, Fair, Serious and Critical, from the platform APIs;
  desktop and web stay Nominal. When the Thermal Response project setting is on (default on for
  Android and iOS):
  - **Serious:** lowers dynamic-resolution max scale by 20% and caps the frame rate at 30 when the
    target is above 30.
  - **Critical:** also uses the next tier down's overrides for shadows and post FX.
  - **Recovery:** after 30 s in a lower state, with hysteresis.
  - Changes are logged and visible to Lua (`Device.thermalState`, event `onThermalStateChanged`).
- **R7. Memory pressure:** `onTrimMemory` (RUNNING_LOW and above), `didReceiveMemoryWarning` and
  the web heuristic each:
  - drop texture streaming's resident mip budget by a level,
  - clear the model and texture CPU caches that can be rebuilt, and unused pools (S06),
  - fire the Lua event `onLowMemory`.
- **R8. Upload pacing.**
  - `SokolCmdQueue` applies a per-frame upload byte budget to image and buffer creation and
    update: Project Settings > Rendering > Upload Budget (MB per frame), defaulting to 8 on
    mobile, 6 on web and 32 on desktop.
  - A single item larger than the budget goes alone in its frame.
  - Large textures with mips are created empty and filled per mip across frames where the backend
    allows it.
  - A monotonic readiness token lets `areScenesLoaded` and screenshots wait for pending uploads.
  - Zero cost when the queue is empty.

### Agent and editor

- **R9. MCP**, added to an existing group with room or a new `device` group:
  - `get_device_info` (read-only, allowed while playing): detected GPU, tier, the reason, thermal
    and memory state, and applied overrides.
  - `set_device_simulation`: `tier`, `platform`, `thermal_state` for Play testing.
  - Tier override table edits go through the existing project settings tools (keys
    `quality.device_tiers.*`).
- **R10. Lua:** `Device.tier`, `Device.gpuName`, `Device.thermalState`, `Device.setTier`, and the
  `onThermalStateChanged` and `onLowMemory` events. Docs go in `docs/scripting.md`.
- **R11. Docs:** `docs/device-tiers.md`, with the agent guide area page included.

### Platform and data

- **R12. Platforms:**
  - Android uses JNI in the existing activity, API level guarded, with a polling fallback for API
    29.
  - iOS and macOS use NSProcessInfo.
  - Web uses JS glue in the existing shell.
  - Desktop reports Nominal.
  - Everything compiles on every target.
- **R13. Old projects:** missing tier settings mean defaults, and the defaults never change a High
  or Ultra device's look.

## 6. Design constraints and decisions

- **Tiers override existing settings** through one resolver (`QualityResolver`) that every
  consumer already reads through, or is changed to read through. There is no second copy of
  settings.
- **Thermal response** acts only on settings marked dynamic (render scale, frame cap, shadow and
  post quality), never on content.

## Decisions

- **A tier never raises quality.** Every cell caps the project's or the scene's value (Render
  Scale, MSAA, Shadow Quality, Shadow Distance, Lit Quality, Target Frame Rate, Max Pixel Lights,
  Particle Budget), Texture Quality drops at least as many mips, and Bloom, SSAO and Volumetrics can
  only be turned off. The LOD biases multiply (contract C4). This keeps R13 by construction: the
  default High and Ultra columns are empty, and no cell can enable an effect a scene did not author
  (nor ask a build for shadow variants it did not cook).
- **The table has one column per tier per platform family** (Desktop, Mobile, Web: the families
  the texture and atmosphere settings already use), not per OS. Android and iOS share Mobile.
- **Shadow LOD Bias is a row too** (C4 resolves it), next to the project-wide `quality.lod_bias` and
  `quality.shadow_lod_bias` (default 1). It is a thermal-critical cell, LOD Bias is not (content).
- **The editor applies no detected tier.** Detection runs in the editor (get_device_info, the
  Project Settings preview), but its views and tests render the project's values until the Game
  view simulates a tier or a script calls `Device.setTier`. Otherwise every editor golden and MCP
  test would depend on the machine's GPU (llvmpipe in CI detects Low). Players apply the detected
  tier once their startup code calls `Device::configure` (the generated `main.cpp` and the prebuilt
  player always do); unit tests never do.
- **Game view simulation** is a toolbar preference (Device: tier, platform family, thermal state),
  applied each frame of Play and ended by Play's stop. The platform family's Auto is Mobile while
  the Game view simulates a phone. The thermal choice is not saved across editor sessions.
- **Thermal Response is a setting per platform family**: on for Mobile, off for Desktop and Web.
  macOS reports NSProcessInfo's state (R12) but does not act on it by default ("desktop ... stays
  Nominal" in R6 is Windows, Linux and the web, which have no signal).
- **Recovery** steps down one state per 30 s spent below the applied state, and any reading at or
  above it restarts the wait. Stepping up is immediate. Critical with no tier applied takes High's
  cells (the project's values count as Ultra).
- **`Device.thermalState` and `onThermalStateChanged` are the platform's state**, so a game can react
  itself; `get_device_info` reports the response's state (`thermal_response`) beside it.
- **Memory pressure** keeps one more mip off streamed textures for the rest of the run
  (`MAX_MEMORY_DROP` 1), clears the pools' unused entries (`Engine::clearUnusedPools`), and fires
  `Device.onLowMemory` at the next frame (`Engine.onLowMemory` still fires at once, as before).
  Several warnings in one frame are one response. Android counts `onTrimMemory` at RUNNING_LOW and
  above except UI_HIDDEN (not pressure). The web warns when the wasm heap passes 90% of its maximum
  or Chromium's `performance.memory` 90% of its limit, re-armed under 80%.
- **Android**: the listener (API 29+) and the game thread's 2 s poll of `getCurrentThermalStatus` and,
  from API 30, `getThermalHeadroom(10)` (at least 1: Serious, at least 0.85: Fair). The poll is the
  fallback where the listener alone reports (API 29). Statuses map light to Fair, moderate to Serious,
  severe and above to Critical. The state crosses JNI as static fields of `JasperPlatform`, the
  pattern the display rotation already uses.
- **GPU names** are matched normalized; the web reads WebGL's unmasked renderer through
  `System::getGpuRendererName` (WEBGL_debug_renderer_info). ANGLE strings carry the PCI device id,
  which the database's PC rows keep. Android's Vulkan ids are dropped (no string JE reads has them).
  The Forge rows with an UNDEFINED preset are left out, and a name with several presets keeps the
  lowest. Vendor defaults do not apply on the web (Safari's "Apple GPU").
- **The re-map**: Forge `verylow` and `office` are Low, `low` Medium, `medium` High, `high` High,
  `ultra` Ultra on every platform; `OVERRIDES` moves the Adreno 630 to 644 and 710 to Medium and the
  Apple A14, A15 and M1 family to High (the script records each reason). Phones never get Ultra from
  the data.
- **The database is embedded** as `GpuTiersData.cpp`, written by the converter from the JSON (chunks
  under MSVC's string-literal limit); `GpuTierTest` checks the embed equals the checked-in JSON and
  `--check` says when either is stale. About 93 KB; parsed once at startup.
- **MCP**: a new `device` group (2 tools within 1,500 characters). `set_device_simulation` is an editor
  preference like `configure_game_view` (not undoable); the table goes through
  `set_project_settings` with one key per family and tier whose value is an object of cells merged in
  (12 keys instead of 168), each change one undo step.
- **Upload pacing** budgets the bytes of MAKE_IMAGE and MAKE_BUFFER with data, UPDATE_IMAGE and
  UPDATE_BUFFER. Waiting commands keep their order; a command on a handle a waiting one creates or
  touches waits with it; a CUSTOM or pass command (the queue's "object loaded" callbacks) never
  overtakes a waiting command, and everything after it waits; a second update of one handle in a frame
  waits (sokol's once-a-frame rule). Cleanups carry the token of the commands queued before them, so
  a deferred upload's pixels and a deferred destroy's dealloc wait for it. The committing thread is no
  longer held while its batch's tail waits.

## Deviations

- **R8, "large textures with mips are created empty and filled per mip across frames where the
  backend allows it"**: no backend allows it through sokol-gfx. An immutable image must be created
  with all its data, and `sg_update_image` updates every mip of a dynamic image at once, once a
  frame (`_sg_validate_update_image`, `_sg_validate_image_data`). Splitting would need a sokol patch
  on all five backends. Instead a texture larger than the budget goes alone in its frame (R8's second
  bullet), and cooked textures already stream small-first (S14's progressive tail).
- **R8's budget covers the queue only**, as R8 says: what loading threads create or update. Textures a
  scene load creates on the main thread are created in the call that needs them, so they are not
  paced; routing them through the queue would change every synchronous creation's contract.
- **R2's "vendor" input**: no backend sokol exposes gives a vendor id; the vendor is read from the
  renderer name (and from ANGLE's PCI ids on the web).
