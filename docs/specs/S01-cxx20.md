# S01 — C++20 migration (all targets, exported project templates)

Wave 0. Lands before every other spec. Every later spec may assume the portable C++20 subset
defined in §6 D7.

## 1. Goal

Make C++20 the language standard everywhere JasperEngine code is compiled: the engine, the editor,
the tests, the vendored C++ libraries we build, the Play plugin the editor generates, and every
exported game (Windows, Linux, macOS, iOS, Android, HTML5). One standard across the whole binary
removes a class of libc++/Wasm template mismatches, lets the ports from OpenEngine (C++20:
`std::span`, defaulted `operator==`, concepts) land without backports, and gives later streams
(S06 job system, S07 ECS, S08 reflection, S18 splines) a fixed language baseline. Projects that
used C++17 move to C++20 automatically when they are opened.

## 2. Scope

In scope:
- The CMake standard knob (`JASPERENGINE_CXX_STANDARD`), its default, its allowed values, and how
  it reaches every target, vendored targets included.
- The hand-maintained Xcode project (`engine/workspaces/xcode`), the Android Gradle project
  (`engine/workspaces/androidstudio`), and the Emscripten, MSVC, GCC and Clang builds.
- What the editor generates: the Play-plugin `CMakeLists.txt` and clangd database
  (`editor/Generator.cpp`), and the exported engine CMake and Xcode/Gradle projects
  (`editor/Exporter.cpp`).
- The project setting (`cxxStandard`): UI, MCP, serialization and migration.
- Source fixes C++20 needs in our code. Also local fixes to vendored code, but only when a library
  does not compile at C++20.
- Minimum toolchain versions and the portable C++20 subset, with a lint that enforces it.
- Docs and tests that state or assume C++17.

Out of scope:
- CMake presets, Werror, sanitizers, unity builds and the unit-test framework. These are S02;
  S01 only makes sure S02 starts from a build with no C++20 warnings in our own code.
- Using new C++20 features in existing code, beyond what is needed to compile. Modernisation
  happens in the specs that touch the code.
- Native toolchain fingerprinting and compile-status UI (S23), and the prebuilt-player export
  (S30).
- C++ modules and coroutines (banned for now, see D7).
- Nothing from OpenEngine's build system is copied. In particular vcpkg is on the do-not-copy list.

## 5. Requirements

### Functional: build system

- **R1** In `engine/CMakeLists.txt`, `JASPERENGINE_CXX_STANDARDS` is `20 23`, and the cache
  default of `JASPERENGINE_CXX_STANDARD` is `20`.
  - A build tree whose cached value is `17` is moved to `20` with `FORCE` and a `message(WARNING
    "JASPERENGINE_CXX_STANDARD 17 is no longer supported; using 20")`.
  - Any other value outside the list is still a `FATAL_ERROR` (`:1133-1136`).
- **R2** `JASPERENGINE_CXX_STANDARD` is the only knob. No CMake file of ours may set a literal C++
  standard. To make that hold:
  - `engine/CMakeLists.txt` sets the normal variables `CMAKE_CXX_STANDARD`,
    `CMAKE_CXX_STANDARD_REQUIRED ON`, `CMAKE_OBJCXX_STANDARD` and `CMAKE_OBJCXX_STANDARD_REQUIRED
    ON` to it before the first `add_subdirectory(libs/…)` (`:708`).
  - The root `CMakeLists.txt` sets the same variables right after `add_subdirectory(${JASPERENGINE_ROOT})`
    (`:471`) and before `libs/nfd` and `libs/yaml-cpp` (`:491-492`), so that both of those use it.
- **R3** Every vendored C++ or ObjC++ target we build gets the engine standard through a single
  helper, `jasperengine_apply_cxx_standard(<targets…>)`. It sets `CXX_STANDARD`,
  `CXX_STANDARD_REQUIRED`, `OBJCXX_STANDARD` and `OBJCXX_STANDARD_REQUIRED`.
  - It replaces the tinygltf/rmlui block at `:1139-1150`.
  - It covers at least: tinygltf, rmlui, joltphysics, shadercompiler and every glslang/SPIRV/
    spirv-cross target it creates, webm, lunasvg, thorvg, soloud, tinyxml2, tinyobjloader,
    harfbuzz, meshoptimizer and sokol.
  - In the editor build it also covers yaml-cpp, nfd and gtest/gtest_main.
  - It is applied after `add_subdirectory`. Vendored `CMakeLists.txt` files are not edited.
- **R4** A configure-time check, `jasperengine_check_cxx_standards()`, runs at the end of every
  top-level configure (editor root, standalone engine, exported game, Android, Web, htmlui-tests).
  - It walks all directories (`SUBDIRECTORIES`, `BUILDSYSTEM_TARGETS`) and looks at every
  library, object library or executable with `.cpp/.cc/.cxx/.mm` sources.
  - It fails with `FATAL_ERROR` and lists the offending targets if any target's `CXX_STANDARD`
    differs from `JASPERENGINE_CXX_STANDARD`. Targets listed in
    `JASPERENGINE_CXX_STANDARD_EXCEPTIONS` are exempt; that list ships **empty**.
  - On success it prints `C++ standard check: <N> C++ targets at C++<std>`.
- **R5** Minimum toolchains are checked by `engine/cmake/JasperEngineToolchain.cmake` through
  `jasperengine_check_cxx_toolchain()`. It is called from `engine/CMakeLists.txt`, which covers
  every engine, export, Android and Web build, and from the root `CMakeLists.txt`.
  - The floors are: GCC ≥ 11, Clang ≥ 16 (also clang-cl, the NDK and Emscripten), AppleClang ≥ 15,
    MSVC ≥ 19.30.
  - The failure message names the detected compiler and version, the floor, and "choose another
    compiler in Preferences > External Tools".
  - The generated plugin `CMakeLists.txt` (`Generator::writeSourceFiles`) emits the same check
    inline, because a plugin has no engine tree to include it from. Its text comes from
    `Generator::getToolchainFloorCheck()`, next to `getEditorPluginAbiCheck()`.
- **R6** MSVC (`CMAKE_CXX_COMPILER_ID` MSVC, or `CMAKE_CXX_SIMULATE_ID` MSVC) adds
  `/Zc:__cplusplus` to all C++ targets. It is added through `add_compile_options` in the engine
  and root CMake, and to the generated plugin's `target_compile_options`
  (`editor/Generator.cpp:1117,1119`).
  - We rely on the conformance mode that `/std:c++20` implies (`/permissive-`). Our targets never
    get `/permissive`.
- **R7** `engine/core/Export.h` gets a language-level guard, inside `#ifdef __cplusplus`:
  `#if defined(_MSVC_LANG)` defines `JASPERENGINE_CPLUSPLUS` as `_MSVC_LANG`, otherwise as
  `__cplusplus`, followed by `static_assert(JASPERENGINE_CPLUSPLUS >= 202002L, "JasperEngine
  requires C++20")`. It reaches every engine translation unit and every plugin translation unit
  (through `JasperEngine.h`), so a plugin built at the wrong standard fails with one clear message.

### Functional: source changes

- **R8** Every `u8string()`, `generic_u8string()` and `fs::u8path(` call in `editor/` (the files
  listed in §3) goes through `FileUtils::pathToUtf8` / `pathFromUtf8`, plus a new
  `FileUtils::genericPathToUtf8`. Afterwards, `grep -rnE 'u8string\(\)|u8path\(' editor engine
  --include=*.cpp --include=*.h --include=*.mm`, excluding `engine/libs/`, matches only
  `editor/util/FileUtils.h`.
- **R9** Our sources compile at C++20 with no C++20-specific diagnostics:
  - GCC: `-Wdeprecated-enum-enum-conversion`, `-Wdeprecated-enum-float-conversion`, `-Wvolatile`,
    and "implicit capture of 'this' via '[=]' is deprecated".
  - Clang: `-Wambiguous-reversed-operator`, `-Wdeprecated-this-capture`.
  - MSVC: C5054, C5055, and C4996 from our own paths.
  - Fixes go in the code. Adding `-Wno-…`, `_SILENCE_…` or `/wd` globally for these is not allowed.
  - Warnings from vendored code stay hidden by `EXTERNAL_WARNING_FLAG`/`SYSTEM` includes.
- **R10** A vendored library that fails at C++20 is fixed by the smallest local patch, marked
  `// JasperEngine: C++20` and recorded in that library's existing JasperEngine notes or patch
  list.
  - If no patch is reasonable, the library may go into `JASPERENGINE_CXX_STANDARD_EXCEPTIONS`,
    but only if three conditions hold:
    1. Its public headers expose no `std::` types to our code.
    2. It is not linked into Web builds.
    3. The reason is commented in place.
  - An MSVC-only conformance failure in a vendored target may add `/permissive` to **that target
    only**.
- **R11** Tooling:
  - All `tools/performance` scripts listed in §3 use `-std=c++20`.
  - The `volatile` compound assignments are rewritten (`x = x + y`).
  - `tools/htmlui/rmlui-tests/CMakeLists.txt` uses 20, because the fork must pass its own tests
    in the mode the engine compiles it in.
  - `tools/htmlui-bench` stays at 17. It compiles no engine sources and no shipped code.

## 6. Design constraints & decisions

- **D1: C++17 is removed, not kept as an option.** Engine API headers, which plugins include
  through `.jasperengine/engine-api`, will use C++20 (`std::span`, concepts) as soon as S06, S07,
  S08 and S18 land, so a C++17 plugin translation unit could not include them.
  - Only 20 and 23 are offered.
  - The engine's public headers must compile at the lowest offered standard (20). CI builds at 20,
    which enforces this.
- **D2: C++23 stays an option**, with no extra CI matrix: one Linux engine-sample build with
  `CXX_STANDARD=23` (AC8), plus an MCP compile at 23. A plugin at 23 linking an engine built at 20
  is supported. It already works at 17/20/23 today, and MSVC STL, libstdc++ and libc++ keep layout
  compatibility across `-std` modes.
- **D3: one standard for the whole binary.** All vendored C++ is compiled at
  `JASPERENGINE_CXX_STANDARD` (R3, R4). This follows the Wasm evidence (commit `7dab6b7e6`) and
  matches the Xcode project, which already builds Jolt and box2d at gnu++20. The exceptions list
  exists but ships empty. C libraries (`C_STANDARD`) are untouched.
- **D4: extensions.** CMake's default `CXX_EXTENSIONS` (ON, so `-std=gnu++20`) is kept, which
  matches today's `gnu++17` behaviour. Xcode uses `gnu++20`. clangd stays on `-std=c++20`; the
  difference has no effect on our code.
- **D5: MSVC flags.** `/std:c++20`, from CMake, implies `/permissive-`. We add
  `/Zc:__cplusplus` everywhere, including plugins, so header-only libraries (nlohmann json,
  LuaBridge3) pick the same code paths in the engine DLL and in the plugin. No
  `/Zc:preprocessor`.
- **D6: toolchain floors** (R5): GCC 11 (Ubuntu 22.04's default), Clang 16, AppleClang 15
  (Xcode 15), MSVC 19.30 (VS 2022), NDK r26 or newer pinned, Emscripten as pinned (6.0.10).
  - CI tests GCC 11 (the floor), current MSVC, current Xcode, the pinned NDK and emsdk 6.0.10.
  - The floors for Clang 16, AppleClang 15 and MSVC 19.30 are declared, not tested in CI.
- **D7: the portable C++20 subset** that every spec may use without platform checks. The binding
  constraints are libstdc++ 11, and libc++ under the macOS 10.15 / iOS 13 deployment targets.

  **Allowed:**
  - Language: concepts and `requires`; `<concepts>`; designated initializers (in declaration
    order, no nesting); `consteval`/`constinit`; `using enum`; defaulted `==` and `<=>` with
    `<compare>`; `[[likely]]`/`[[unlikely]]`; `[[no_unique_address]]`; template lambdas; class
    types as non-type template parameters (structural types only).
  - Library: `std::span`; `<bit>` (`bit_cast`, `popcount`, `countl_zero`, `bit_ceil`,
    `has_single_bit`, `endian`); `<numbers>`; `std::ssize`; `contains`; `starts_with`/`ends_with`;
    `std::erase`/`erase_if`; `std::to_array`; `std::midpoint`/`lerp`; `<source_location>`;
    `std::is_constant_evaluated`.
  - Ranges: the algorithms, plus the views `filter`, `transform`, `iota`, `reverse`, `take`,
    `drop`, `keys`, `values`, `elements`, `split`, `join`, `common`, `all`.

  **Banned** (needs GCC ≥ 12/13 or macOS ≥ 11/13.3/14):
  - `<format>`/`std::format`. Logging (S09) uses printf-style formatting.
  - `std::jthread`, `std::stop_token`/`stop_source`.
  - `std::atomic::wait`/`notify_*`, `<semaphore>`, `<latch>`, `<barrier>`. S06 uses
    `std::condition_variable`/`std::mutex`.
  - `<memory_resource>`/`std::pmr`. S06 allocators are our own.
  - Floating-point `std::to_chars`/`from_chars`.
  - `<syncstream>`.
  - `std::string`/`std::vector` inside constant evaluation.
  - `std::atomic<std::shared_ptr>`; `std::atomic<float>` `fetch_add`.
  - `<chrono>` calendars and time zones.
  - Coroutines, modules, and every C++23 library addition.

  This list is the contract. R26 lints the part of it that can be found by pattern; Apple CI
  catches the rest (atomic waits, `to_chars` on floats).
- **D8: no C++17 shims.** No `#if __cplusplus >= 202002L` branches in engine or editor code.
  `FileUtils.h`'s `__cpp_lib_char8_t` branch reduces to the C++20 path.
- **D9: the floor check is code, not docs.** S23 (toolchain fingerprint) reuses
  `JasperEngineToolchain.cmake` and `getToolchainFloorCheck()` rather than duplicating floors.
- **API sketches**, using existing names where possible:
  ```cmake
  # engine/cmake/JasperEngineToolchain.cmake
  function(jasperengine_check_cxx_toolchain)        # FATAL_ERROR below the R5 floors
  function(jasperengine_apply_cxx_standard)          # ARGN: targets; sets CXX/OBJCXX standard
  function(jasperengine_check_cxx_standards)         # R4 walk; honours JASPERENGINE_CXX_STANDARD_EXCEPTIONS
  ```
  ```cpp
  // editor/util/CxxStandards.h
  inline constexpr int cxxStandards[] = { JASPERENGINE_CXX_STANDARD_LIST };   // {20, 23}
  // editor/Exporter.h
  static bool applyXcodeCxxStandard(std::string& pbxproj, int standard);    // false: no setting found
  // editor/Generator.h
  static std::string getToolchainFloorCheck();
  ```

## 9. Risks & defaults

| Risk / open question | Default decision |
|---|---|
| MSVC's implied `/permissive-` exposes an unknown number of errors in Windows-only editor and engine code (Windows CI runs only on demand) | Fix our code. A vendored target may get `/permissive` alone (R10). Start the Windows CI run first, because it is the long pole |
| A vendored library (glslang, spirv-cross, soloud, the RmlUi fork, Jolt) fails or misbehaves at C++20 | Minimal local patch marked `// JasperEngine: C++20` (R10). The exception list only under its three conditions. RmlUi must also pass its own suite (AC7) |
| libc++ availability errors (macOS 10.15 / iOS 13) are caught only by the on-demand Apple CI | D7 contract plus the R26 lint on every push. Specs touching threading (S06) run the macOS job before merging |
| User C++ scripts written for C++17 break after the automatic switch | Accepted. R20 warning plus the "Moving from C++17" doc section. Errors appear through the existing compile path. No opt-out to 17 (D1) |
| GCC 11 lacks C++20 library parts that later specs want (`<format>`, constexpr containers) | Banned in D7. Raising the floor is a separate decision (§8 README note) |
| C++23 Xcode setting values on older Xcode | C++23 Apple exports need Xcode ≥ 16 (tooltip, R19). CI covers 20 only |
| Plugin at 23 linking an engine built at 20 | Supported (D2). Tested by AC12 on Linux only |
| ccache and every build tree rebuild from scratch once | Expected one-off cost. R1 migrates cached 17 automatically |
| The exact NDK version string to pin is not in the repo | Pin the version CI's AGP 9.4.1 resolves now (R14). Must be ≥ r26 |
| Build time grows past the budget | If AC20 fails, profile the slowest translation units and fix them in S01, by reducing includes (for example in `editor/mcp/tools/WorldTools.cpp`) rather than reverting the standard |

## Deviations

Recorded by the S01 implementation.

- **R3 helper.** Besides `jasperengine_apply_cxx_standard(<targets…>)` there is
  `jasperengine_apply_cxx_standard_in_directories(<dirs…>)`, which applies it to every C++ target
  under a vendored directory. It is used for `libs/shadercompiler`, so a glslang/spirv-cross target
  added by an update is covered without a list. In this tree glslang, SPIRV and spirv-cross compile
  inside the single `shadercompiler` target.
- **R5 floors.** `JasperEngineToolchain.cmake` names the floors after `CMAKE_CXX_COMPILER_ID`
  (`JASPERENGINE_CXX_FLOOR_GNU`, `_Clang`, `_AppleClang`, `_MSVC`). The root `CMakeLists.txt` passes
  them to the editor targets as compile definitions, so `Generator::getToolchainFloorCheck()` and
  the Project Settings tooltip take the numbers from that file. The floors have one source (D9).
- **R11.** `tools/performance/base64.cpp:90-91` has no compound assignment on a `volatile`
  (`checksum` is a plain `size_t`), so it is unchanged. The volatile compound assignments are in
  `instance-sort.cpp`, `string_utils.cpp`, and in the C++ that `console.py`, `hierarchy.py` and
  `text_search.py` write out. Those were rewritten.
- **R12.** A build with `CXX_STANDARD=<n>` uses its own directories (`build/linux/editor-cxx<n>`,
  `build/linux/engine-cxx<n>`, `build/web/cxx<n>`). A C++23 run therefore does not leave the
  default trees cached at 23, and the next default build does not rebuild everything.
- **R20.** Any unsupported value logs the same warning and moves to 20, not only values below 20.
- **AC10/AC11 fixture.** No separate fixture project is committed. `test_cxx_standard.py` adds the
  C++ script to its scratch copy of the default fixture, which has no `cxxStandard`, then copies
  that project with `cxxStandard: 17` and opens the copy. The Play plugin's generated
  `CMakeLists.txt` is at the project root (`Generator::writeSourceFiles`), not in
  `.jasperengine/build`, which is the build tree. The test reads it there.
- **AC12.** `if consteval` needs GCC 12, and the supported floor (and the build image) is GCC 11.4.
  The C++23 script instead uses the `uz` size_t literal suffix (P0330, GCC 11) and
  `static_assert(__cplusplus > 202002L)`. That proves the Play build ran at C++23.
- **AC21.** `docs/mcp/TOOLS.md` is generated from the tool list. Setting keys and their
  descriptions are not in it, so it has no `scripting.cxx_standard` entry. `test_cxx_standard.py`
  checks the key's "20 or 23" description through `get_project_settings describe`.
- **Found by S01 beyond §3.** `requires` is a keyword in C++20, and it was used as an identifier in
  the HTML UI tests (`engine/tests/htmlui/compat/BrowserCompare.*`,
  `compat_golden_pages_test.cpp`). It is renamed to `requiredFeatures`.
- **R14.** The pinned NDK is `28.2.13676358` (Clang 19.0.1). It is the version AGP 9.4.1 installed
  in the Android build image, which is the same Gradle setup CI uses.
- **AC20 measurements.** Taken on the remote servers, Release builds with the same image and flags.
  - Linux `jasperengine-project`: 40,685,792 bytes at C++17 (`e71140fbf`) and 40,859,664 bytes at
    C++20, a ratio of 1.0043.
  - Web `jasperengine-project.wasm`: 29,595,707 bytes and 30,122,187 bytes, a ratio of 1.0178.
  - The clean editor build-time ratio (ccache off) was not measured. Both servers were saturated by
    the other streams' builds, so a wall-clock comparison would have measured the load, not the
    standard. It should be taken on an idle runner, for example in CI.
- **Not verifiable here.** AC4, AC5 and AC6 need the Windows and macOS CI jobs, which are not
  available to this stream. The Windows and Apple code paths were reviewed by reading: there are no
  `u8` literals, mixed-enum arithmetic, `volatile` compound operations, `[=]` this-captures or
  `/permissive-` violations in our code. The CI `linux` job gets the subset lint and the AC15/AC16
  checks.
